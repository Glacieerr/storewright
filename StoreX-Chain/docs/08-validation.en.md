# Validation: against theory, exact optima, classic algorithms and similar tools

[中文](08-validation.md)

> This project is not affiliated with any retailer or company. All data is synthetic; the models are not calibrated against real operations and must not be used for real production decisions.

This page answers one question: **how far can the algorithms and formulas inside the simulator and the dispatch board be trusted?** The method is to compare them with things whose answers are known:

| What | Compared with | Where |
|---|---|---|
| Store delivery routing (Clarke–Wright savings, `src/sim/routing.ts`) | The **exact optimum** of the same instance, and the common **nearest-neighbour** greedy | Section 1 |
| The fill-rate formula used for allocation (`src/network/allocate.ts`) | **Monte Carlo simulation** and textbook values of the **standard normal loss function** | Section 2 |
| The three dispatch-board solvers and the multi-store network planner (all claim exact optimality) | **Exhaustive enumeration** | Section 3 |
| The duty assistant | **Other systems** on the same blind test sets (keyword rules, nearest-neighbour retrieval, naive Bayes, and an LLM you connect yourself) | [Duty-Desk Bench](benchmark.en.md) |
| Overall positioning | 12 **similar open-source projects** | Section 5 |

## Reproduce

```bash
cd StoreX-Chain
npm run validate              # run every comparison (a few seconds) and print a summary
npm run validate -- --write   # also write bench/validation/ and the generated part of this page
npm run validate -- check bench/validation/cvrp/sx-cvrp-n10-001.vrp your.sol   # check another solver's result
```

Apart from timings, every number is deterministic (the random instances use fixed seeds). Timings are reference values from the author’s machine and vary slightly between runs.

### Problems found and fixed by this validation

- **The door-assignment solver used one door too many** (2026-11-07): on the first run, “Dock doors: fewest role mismatches and doors used” disagreed with exhaustive search on 3 of 200 instances — same number of role mismatches, one more door. When one door class is short, a fast path that moves trucks to the other class returned its result even when it could not prove the door count minimal (the solver did flag those results as “not proven optimal”). It now continues with the exact search in that case and keeps the better result; all 200 instances match exhaustive search, and neither the real day on the dispatch board nor the duty-assistant evaluation changed (with default facilities a different, provably optimal fast path is used).

## 6. Not validated yet (stated plainly)

- **Traffic-flow accuracy.** Regional traffic is a simplified model (the region is compressed 1:10) and has not been compared with a professional traffic simulator such as SUMO. Doing so needs a SUMO installation (a large download); the same road network and flows could be exported and travel times and queue lengths compared.
- **Calibration with real data.** The data is synthetic and parameters follow public standards (see the module comments and [docs/01-planning-report.md](01-planning-report.md)). A next step is a rough calibration against published annual statistics (port throughput, air cargo volumes) with the method written down.
- **Head-to-head runs against other routing solvers.** The instance files in section 4 are in the standard format, but VROOM, OR-Tools and similar tools have not been installed and run on this machine yet (extra downloads).
- **The optional LLM mode.** The code and the step-by-step guide exist ([docs/06-llm-option.md](06-llm-option.md)); the benchmark has not been run with a real model account.
