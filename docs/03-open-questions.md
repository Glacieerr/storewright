## G · 全局与战略

**G-01 [阻塞] 项目定位是什么？**
作品集展示 / 开源参考实现 / 商业产品，三者在合规要求、深度、硬件投入、许可证上差异巨大。
- 为什么尖锐：如果是商业产品，知识产权、许可证和专利会成为首要问题；如果是作品集，就没必要真的去采购传感器硬件。
- 建议默认：**开源参考实现 + 作品集**。软件完整可运行，硬件部分用仿真与接口规范替代，并预留真实硬件接入层。
- **答复**：以开源参考实现 + 作品集为主，同时做好随时转为商业化项目的一切准备。

**G-02 [阻塞] 是否接受「净室（clean-room）」原则？**
参考大型零售商的公开做法时，如果复制其界面、分配逻辑或内部术语，可能涉及商业秘密、版权（UI）和商标问题。
- 为什么尖锐：这是唯一可能让项目**被迫下线**的环节，比任何技术问题都优先。
- 建议默认：
  1. 只使用**公开信息**（官方新闻稿、公开专利、行业通用知识）和对**通用作业流程**的理解；
  2. **不使用**任何内部资料、内部指标、内部系统代号；
  3. UI **全部原创**，不模仿任何现有系统的布局和配色；
  4. 产品名与模块名**中性化**，不含任何第三方商标（模块直接叫 Pick / Stage / Dispense）；
  5. 文档中写明「本项目与任何零售商无隶属关系」。
- **答复**：接受。只使用公开信息与作者对通用工作流的理解和方案；不使用任何内部截图、代号；UI、UX、logo、icon 全部重新设计；产品名、模块名采用中性化 / 个人化方案；文档写明「本项目与任何零售商、企业无隶属关系」。

**G-03 [阻塞] 目标门店画像是什么？**
美国大型超市（Supercenter，约 15–20 万平方英尺，十万级 SKU）/ 社区超市（Neighborhood Market）/ 区域连锁超市 / 中国生鲜超市或前置仓？
- 为什么尖锐：大型零售商已经有成熟的系统（并已对外出售），新系统对它们的**边际价值很低**；真正缺这类系统的是**中型区域连锁和独立超市**。定制化的维度、默认参数、法规（FDA / 中国食品安全法）都由这里决定。
- 建议默认：**以美国中型超市为默认模板**（约 3–5 万 SKU、单层、有后仓），同时提供「大型超市」模板，并用配置证明它能扩展。
- **答复**：改为以**中型区域连锁和独立超市**为模板；向上可扩展承接大型门店，向下覆盖小型门店；定制化是必须的。

**G-04 [重要] 地域与法规基准？**
- 建议默认：美国（FDA Food Code、OSHA/NIOSH、各州劳动法）。中文/英文双语界面，单位支持 lb/kg 切换。
- **答复**：采纳建议默认。

**G-05 [阻塞] 系统是「替换」还是「叠加」？**
成熟门店已有 POS、ERP、商品主数据、劳动力排班（WFM）、电商订单系统（OMS）。本系统要么替换其中一部分，要么作为中间层通过接口集成。
- 为什么尖锐：现实中没有门店会因为一个新系统把 POS 和 ERP 推倒重来。「能否集成」决定了它能否落地。
- 建议默认：**叠加**。系统负责门店内的履约执行层（拣货 / 暂存 / 交付 / 后仓 / 补货 / 人员调配），对外通过标准化的**适配器接口**接入订单、商品主数据、POS 销售流水和退款；演示时由模拟器提供这些外部数据。
- **答复**：叠加。替换成本过高，现阶段也没有必要（尽管一站式替换在理想状态下是最佳方案）。

**G-06 [阻塞] MVP 范围？**
需求描述的范围相当于 WMS（仓储）+ OMS 履约 + WFM（人员）+ IoT 平台 + 数字孪生 + 推荐系统，商业公司通常需要几十人做数年。
- 为什么尖锐：如果十二个模块平均用力，结果会是十二个半成品。
- 建议默认：分三层交付。
  - **核心（必须做透）**：Picking（含容量分配）→ Staging → Dispensing → 标签全链路，外加可配置的门店模型和 2.5D 模拟器。
  - **扩展（做到可用）**：后仓库存、Exception、GMD / Oversized、MTO、替代推荐、AI 人员调配。
  - **前瞻（以仿真和接口规范为主）**：货架传感器补货、IP 包裹、退货。
- **答复**：采纳建议默认。

**G-07 [重要]「零延迟」的工程定义？**
物理上不存在零延迟。需要可量化的指标。
- 建议默认：本地交互（点击、拖拽、视角切换）**60 fps**，单帧 < 16 ms；同一门店内设备间状态同步 **p95 < 200 ms**；模拟器在浏览器中能以 1×–60× 加速运行，且不掉帧。
- **答复**：采纳建议默认。

**G-08 [阻塞] 源码到底开不开源？**
原始需求是「除了软件源代码外，其他部分上传至 GitHub」。但模拟器要在个人网站上运行，浏览器端 JavaScript 打包后任何人都能查看；README 和 pseudo code 也会暴露大部分设计。
- 为什么尖锐：「半开源」在技术上很难真正保护源码，还会降低作品集的说服力（招聘方更愿意看真实代码）。
- 建议默认：两个仓库。
  - **公开仓库**：文档、README、伪代码、领域模型、配置示例、效益分析报告、模拟器的构建产物（或完整源码）。
  - **私有仓库**：后端服务和移动端源码。
  - 许可证建议：文档用 CC BY 4.0，代码（如公开）用 Apache-2.0。
- **答复**：委托决定，依据：作品集说服力、招聘方视角、商业化打包出售。结论见 [决策记录 0001](decisions/0001-phase0-decisions.md) 第 2 节（开放核心 + 双许可）。

**G-10 [阻塞] 信息来源的边界是什么？**
公开资料查不到的环节（例如暂存位编码、交付看板、等待时间目标）很多，需要明确设计依据从哪里来。
- 为什么尖锐：边界不清，就无法证明设计是独立完成的。
- 建议默认：只使用公开资料 + 消费者可观察到的流程 + 合理推测；公开资料查不到的环节一律作为自主设计，并标注【设计】；商业化之前完成法律与专利复核。
- **答复**：转换思路：以「观察细致、有想法的长期消费者」视角推进项目；流程、范围、步骤可以适当简化，按合理推测进行规划和完善。

**G-11 [重要] 是否对相关专利做规避设计？**
门店履约领域已有多项公开专利，覆盖分批拣货、框容量分配、到店检测、ETA 驱动的准备、替代推荐等方法。美国专利法没有非商业用途豁免。
- 建议默认：实现分批装箱、ETA 驱动准备、替代提示等具体方法前，先阅读相关专利的权利要求并做规避设计；规避分析作为私人记录保存，不公开（公开写明重叠关系相当于公开承认）。
- **答复**：必须做规避设计。目标转向中型与独立市场后，结合扩展性、独立规划等特性，做新的方案设计和专利规避。

**G-09 [重要] 个人网站现状？**
是否已有网站、用什么技术栈、托管在哪里（GitHub Pages / Vercel / Netlify / 自有服务器）？
- 为什么尖锐：如果是纯静态托管，模拟器必须**完全在浏览器内运行**（仿真引擎跑在 Web Worker 里），不能依赖后端。这是一个硬性的架构约束。
- 建议默认：**模拟器纯前端可运行**；「实时运营模式」作为可选部分，连接自托管后端。
- **答复**：已有网站 yecanyuan.com：公共网站与 Web 管理端为原生 HTML / CSS / JavaScript；服务端为 Vercel Functions；结构化内容为 GitHub 仓库中的 JSON；媒体与下载文件在 Vercel Blob；发布流程为 Git + GitHub Pull Request + Vercel；域名解析为 Cloudflare DNS。

## O · 订单接入与时段

**O-01 [重要] 时段（slot）长度是否固定为 1 小时整点？**
原始需求的例子：预计 12:34 来取货，标签显示 12:00（12:00–1:00 时段）。
- 建议默认：时段长度可配置（30 / 60 / 120 分钟），默认 60 分钟；标签显示时段起点。
- **答复**：时段长度可配置为 60 分钟或 120 分钟。

**O-02 [重要] 是否需要「时段容量管理」？**
调人只是解决忙闲问题的一半，另一半是**控制接单量**：每个时段能接多少单，应由门店的产能（在岗人数 × 人均效率）反推。
- 为什么尖锐：如果系统只调人不控单，高峰时段再怎么调也会爆仓。
- 建议默认：系统对外输出每个时段的**建议产能上限**（以商品件数计），由订单平台决定是否采纳；模拟器中可以打开或关闭这个功能，用来对比效果。
- **答复**：采纳建议默认。

**O-03 [重要] 订单修改截止点？**
顾客在拣货开始后加购、删减或取消怎么办？
- 建议默认：时段开始前 N 小时锁单（可配置，默认 2 小时）；锁单后的修改一律作为异常处理；已拣商品退回货架时生成「回架任务（restock task）」。
- **答复**：采纳建议默认。

**O-04 [重要] Express（加急，例如 1 小时内送达）订单如何插队？**
- 建议默认：Express 单可以插入正在生成的批次；若无法合批，则单独开一个小批次（例如 2–4 个框的轻推车）；已在路上的推车不重排。
- **答复**：采纳建议默认。

**O-05 [可后定] Delivery 订单的时间锚点是什么？**
是司机到店时间，还是顾客收货时间窗？Staging 截止时间需要由这个锚点倒推。
- 建议默认：以**司机预计到店时间**为锚点；没有司机信息时，用「收货时间窗起点 − 配送时长」估算。
- **答复**：采纳建议默认。

## P · Picking（拣货）

**P-01 [阻塞] 原始需求列出的 13 个「类别」其实是四个不同维度，需要拆开。**
杂货、冷藏、冷冻、大尺寸、超大多人协作、服饰、电子、家居、工具、户外、节日、熟食……这里混合了：
1. **温区**：Ambient / Chilled / Frozen / Hot
2. **处理方式**：标准 / 大件 / 多人搬运 / 易碎 / 化学品 / 年龄限制 / 高价值上锁
3. **商品类别**：杂货 / 服饰 / 电子 / 家居 / 工具 / 户外 / 节日……
4. **履约类型**：Grocery / GMD / MTO / IP

- 为什么尖锐：如果把它们放在同一个枚举里，「冷冻的大件」或「需要上锁的电子产品 + GMD」这类组合就无法表达，分配逻辑会越写越乱。
- 建议默认：每个 SKU 带**四个独立属性**。分配逻辑主要依据「温区 + 处理方式 + 履约类型」；「商品类别」用于路径规划、仓库分区和替代推荐。
- **答复**：采纳建议默认。

**P-02 [阻塞] 一辆推车是否只装一个温区？**
- 建议默认：**是**。拣货批次（pick walk）按温区生成，冷冻批次放在最后执行；同一订单的常温、冷藏、冷冻部分会分别出现在不同推车上，到 Staging 时再按订单号汇合（但物理上仍分温区存放，见 S-03）。
- **答复**：是。拣货批次按温区生成：常温同车、冷藏同车、冷冻同车。

**P-03 [阻塞]「8 个框 = 8 个订单」还是「8 个框 = 8 个子单」？**
大订单一个框装不下怎么办？原始需求中「可以来源于同个用户的不同订单」是否意味着允许一个框混装多个订单？
- 为什么尖锐：一个框混装两个订单，两单的取货时间、取消状态、交付对象可能都不同，交付时极易出错。
- 建议默认：订单 → 按温区拆成「履约段」→ 按容量拆成「框任务（tote assignment）」。**一个框只属于一个订单**；一个订单可以占用多个框（标签显示「2/3」）；同一顾客的多个订单仍然分框，但在 Staging 时就近放置，在 Dispensing 时合并展示。
- **答复**：采纳建议默认。

**P-04 [阻塞] 容量计算的规则与数据来源？**
「必须小于取货框的大小」在现实中远不够：
1. 商品尺寸主数据经常缺失或不准；
2. 形状不规则时，体积利用率不可能达到 100%；
3. 体积小但很重的商品（罐头、饮料）会先触到**重量**上限；
4. 有压放约束（鸡蛋、面包、薯片不能被压）；
5. **化学品与食品必须隔离**（漂白剂、清洁剂不能和食物同框，这是食品安全常规）。

- 建议默认：同时满足以下全部条件才允许装入：
  `体积 ≤ 框容积 × 装填系数(默认 0.70)` **且** `重量 ≤ 框重量上限(默认 35 lb，可配置)` **且** 易碎品单独标注并放在上层 **且** 化学品单独装框。
  尺寸缺失时按品类的平均尺寸估算，并标记「尺寸待校准」；拣货员可以一键反馈「装不下」，系统据此在线修正装填系数。
- **答复**：采纳建议默认。

**P-05 [重要] 称重商品（随机重量）怎么处理？**
肉、蔬果按重量计价，顾客下单「约 2 lb」，实际拣出 2.3 lb。
- 建议默认：允许 ±X% 的偏差（可配置，默认 ±10%）；扫描随机重量条码（价格或重量嵌入型 UPC）时自动读取实际重量；偏差超出范围时提示拣货员增减；最终价格差异作为事件推送给订单系统。
- **答复**：使用称重设备获取实际重量，按「重量 × 单价」计算最终价格。

**P-06 [阻塞] 商品位置数据的准确性如何保证？**
拣货路径优化完全依赖「商品在哪个货架、哪一层、哪个位置」的数据。现实中商品经常不在系统记录的位置，而且同一商品可能出现在多个位置（主货架、端架、促销堆头、季节区）。
- 为什么尖锐：位置数据不准，所有路径优化都会变成负优化。
- 建议默认：
  - 每个 SKU 支持多个位置，并区分主位置和副位置；
  - 拣货员**每次扫描商品**都会隐式确认该位置（被动校准）；
  - 若在 A 位置找不到、却在 B 位置扫到，系统自动更新位置并记录；
  - 位置置信度随时间衰减，置信度低的位置触发核查任务。
- **答复**：采纳建议默认；另外，**补货上架时**就必须扫描并确认商品摆放位置。

**P-07 [重要] 多件同品是逐件扫描还是输入数量？**
例如 30 盒酸奶。
- 建议默认：扫描一次后输入数量；数量超过阈值（默认 6）时，要求再随机扫描一次进行抽检。
- **答复**：采纳建议默认；Oversized 商品由员工确认自己能装载的最大数量并输入设备，系统据此把剩余件数派发给其他员工。

**P-08 [阻塞] 缺货（Item Not Found）时，推车上的其他 7 个订单怎么办？**
Exception 去后仓取货可能需要 5–15 分钟。拣货员不能停在原地等。
- 建议默认：缺货处理分为**异步**的三条路：
  ① 顾客允许替代 → 立即推荐附近的替代品；
  ② 后仓有货且该商品重要 → 生成 Exception 任务，派给授权员工，取到后直接送到 Staging 的对应订单位置「补框」，拣货员继续往下走；
  ③ 都不行 → 标记缺货，通知顾客。
  这三条的优先顺序和触发条件可配置。
- **答复**：采纳建议默认。

**P-09 [重要]「节日类」不应是固定类别。**
- 建议默认：节日是**动态标签 + 季节性区域**（例如「万圣节 2026」标签挂在若干 SKU 上，季节区在平面图上可以随时重新划定），而不是写死的一个类别。
- **答复**：采纳建议默认；季节区规划在固定位置，节日轮替时直接更换商品。

**P-10 [重要] 上锁 / 高价值商品（电子产品、部分化妆品、酒类）如何拣？**
- 建议默认：此类商品拣货需要「授权员工」或「钥匙持有人」；系统将其单独拆为一个小任务，并在交付时要求再扫描一次。
- **答复**：采纳建议默认。

**P-11 [重要] 超大件、多人协作商品从哪里拣？**
家具、电视、床垫、自行车通常存放在后仓或高层货架，可能需要叉车（PIT）或梯子，涉及操作资质。
- 建议默认：此类商品不进入常规拣货，而是生成「大件任务」：指定 2 人、要求相应资质、直接从后仓位置拣到大件暂存区。
- **答复**：采纳建议默认。

**P-12 [重要] 冷链计时？**
冷冻或冷藏商品离开冷柜后，到放入 Staging 冷柜之间的最长时间是多少？
- 建议默认：系统从批次中第一件冷冻商品被扫描时开始计时，超过阈值（可配置，研究结论见 `02-feasibility.md`）时告警，并建议拣货员立即回 Staging。
- **答复**：从第一件冷藏 / 冷冻商品被扫描并放入拣货框时开始计时，**上限 1 小时**；可按批次待拣商品总量动态调整。

**P-13 [重要] 标签预先打印的风险？**
标签打印后订单被取消或修改；标签贴错框；打印机故障。
- 建议默认：标签打印后在推车上**扫描框号进行绑定**（标签 ↔ 框 ↔ 订单）；订单被取消时，系统提示作废对应标签；标签带「版本号」，重打后旧标签自动失效（见 L-04）。
- **答复**：保留预打印标签。订单中途取消时，在暂存环节于员工设备上提示「该订单已取消」，并提示将商品放到回收专区。

**P-14 [可后定] 推车中途满了怎么办？**
- 建议默认：容量分配阶段就应避免；若实际装不下，拣货员点击「框满」，系统把剩余商品拆到新框（同订单），并提示回 Staging 卸货或继续。
- **答复**：采纳建议默认；提示返回并结束本次拣货即可，无需继续。

## GM · GMD 与 Oversized

**GM-01 [阻塞] GMD / Oversized 的阈值要变成规则，而不是举例。**
「2 袋或以上融雪盐」「单袋 > 30 lb」「30 瓶或以上矿泉水」只是例子。
- 建议默认：规则引擎，所有阈值可配置：
  - 单件重量 > 30 lb → Oversized；
  - 单件任一边长 > 框内径 → Oversized；
  - 订单内同 SKU 合计重量 > 50 lb → Oversized；
  - 品类黑名单（蔬果、冷藏、冷冻、熟食）→ 不得进入 GMD；
  - 其余非食品 → GMD。
- **答复**：采纳建议默认；重量阈值按普通成年人正常搬运的重量设定，不能过重，避免受伤。

**GM-02 [重要] GMD 订单由谁配送？**
和杂货 Delivery 是同一批司机吗？还是走快递 / 承运商？
- 建议默认：配送方式作为订单属性（自有司机 / 第三方平台 / 承运商）；GMD 的 Stage 和 Dispense 独立运行，但可以和同一顾客的杂货订单**合并交付**（可配置开关）。
- **答复**：GMD 订单与其他订单**分开配送，不允许混合**；当前时段 GMD 单量过少时，可与后续时段的 GMD 订单合并。

**GM-03 [重要]「先扫后打」的标签粒度？**
3 箱水是 1 张标签还是 3 张？
- 建议默认：**一件一签**，显示「1/3、2/3、3/3」；扫描任一件都能找到同组的其他件。
- **答复**：一件一签。

**GM-04 [可后定] 便携打印机的管理？**
电池、纸卷、蓝牙配对。
- 建议默认：打印机作为设备资产登记，员工登录时绑定；系统记录电量和故障情况。
- **答复**：采纳建议默认。

## S · Staging（暂存）

**S-01 [阻塞] 位置编码规则？**
- 建议默认：`区域-架-层-格`，例如 `AMB-03-2-B`、`CHL-01-4-A`、`FRZ-02-1-C`；大件区只有区域级编码，例如 `OVS-Z1`。每个格的容量（可放几个框）可配置。编码规则本身也可配置。
- **答复**：默认「区域-架-层-格」（例如 `AMB-03-02-16`），管理员可以自定义。

**S-02 [阻塞] 位置是系统指定还是员工自选？**
- 建议默认：**系统推荐 + 扫描确认 + 允许覆盖**。推荐时优先考虑同订单已占用的相邻格位，其次是靠近交付出口的位置（按取货时段先后排列）。员工可以覆盖推荐，覆盖次数作为优化数据。
- **答复**：以「**员工自选** + 扫描确认 + 允许覆盖」为主（空间常被临时占用）；格位、区域都没有变化时可以使用系统推荐，但员工自选始终保留。

**S-03 [重要]「相同订单号放在一起」只能在同一温区内实现。**
冷冻框必须放在冷冻柜，冷藏框必须放在冷藏柜。
- 建议默认：同订单的框在**各自温区内**相邻放置；系统为每个订单生成一张「跨温区位置清单」，Dispensing 时一次显示全部位置。
- **答复**：采纳建议默认。

**S-04 [重要] 大件「不需要编号」会导致找不到。**
- 建议默认：大件不编到格位，但必须扫描**区域标签**（例如 `OVS-Z1`），以便 Dispensing 时知道去哪个区域找。
- **答复**：采纳建议默认。

**S-05 [重要] Staging 满了怎么办？**
- 建议默认：系统实时显示各温区的占用率并做预测；占用率超过 85% 时提醒管理员，并启用溢出区；这也是 O-02 时段容量管理的一个输入。
- **答复**：采纳建议默认；冷冻区、冷藏区使用同样的策略。

**S-06 [重要] 订单未取（no-show）怎么办？**
- 建议默认：超过取货时段 + 宽限期（可配置，默认次日关店）后自动取消；生成回架任务；冷藏、冷冻商品按食品安全规则判定能否回架（见 02 文档中的研究结论）。
- **答复**：采纳建议默认。

**S-07 [可后定] 是否需要「并框」功能？**
多个半空框合并以节省空间。
- 建议默认：允许同订单、同温区并框，扫描后更新绑定关系。
- **答复**：采纳建议默认；系统根据框编号提示可以并框的组合。

**S-09 [重要] 暂存冷柜是否需要连续温度记录？**
食品检查看的是食品本身的温度（冷藏 ≤ 41°F）。
- 建议默认：每个冷藏柜、冷冻柜、保温柜接入温度传感器（模拟器中仿真），探头放在最暖的位置，超温告警，日志可供检查；冷柜故障时系统自动列出受影响的订单。
- **答复**：采纳建议默认。

**S-08 [重要] Pickup 区 / Delivery 区是物理隔离，订单类型变化怎么办？**
例如顾客把 Pickup 改成 Delivery，或者司机取消后重新派单。
- 建议默认：订单类型变化时生成「移位任务」；非高峰期可以不移位，只在系统中更新类型。
- **答复**：设置锁单时间，超过后不得修改交付方式；司机取消或退回门店后，由门店重新选择交付方式。

## D · Dispensing（交付）

**D-01 [阻塞] 四位数验证码的安全模型？**
4 位只有 10,000 种组合。
- 为什么尖锐：如果允许「输入验证码查找订单」，在 200 个未完成订单的情况下，**随便猜一个号码就有约 2% 的概率命中某个订单**。
- 建议默认：验证码用密码学安全的随机数生成，未完成订单之间不重复；员工必须**先定位订单**（姓名、车位或扫描），**再输入验证码核验**，绝不允许凭验证码查找订单；只在该订单「已到达」状态下有效；每单最多尝试 3 次，失败后转为人工核验（姓名 + 订单号后四位）；司机多单时**每单一个码**。
- **答复**：采纳建议默认。司机端增加「**行程**」机制：一个行程包含 2–4 个订单，由系统 / AI 根据商品数量、重量组合；司机接收整个行程，一个行程只需一次验证码。

**D-02 [阻塞] 交付流程的完整顺序？**
原始需求的顺序是：验证码 → 再次扫描所有标签 → 告知缺货 / 替代 → 完成。缺少两个现实步骤：
① **顾客当场拒收替代品**（需要退款处理）；
② **年龄限制商品（酒类）的身份核验**。
- 建议默认：
  `到达 → 验证码 → 逐框扫描（核对数量）→ 年龄核验（如有）→ 告知缺货与替代 → 顾客接受/拒收替代 → 装车 → 完成`。
  拒收的商品生成回架任务和退款事件。
- **答复**：采纳建议默认。替代品：顾客**下单时**即明确告知「替代商品只能在收货后发起退货退款」，交付时不做当场拒收，以简化流程。

**D-03 [重要]「距离多长时间抵达」的数据来源？**
需要顾客 app 共享位置（需授权），或者第三方配送平台（如 Uber、DoorDash 等）提供司机 ETA。第三方平台的 ETA 本系统**拿不到**，除非对方开放 API。
- 建议默认：定义标准化的「到达事件接口」（ETA 更新 / 已到达 / 车位号）；模拟器中模拟 ETA；真实接入时由适配器对接各个平台。
- **答复**：司机 / 顾客开启 GPS，结合 Google Maps（或其他实时地图导航工具）、开源项目和 AI 共同估算到达时间。

**D-04 [重要] 三色状态与阈值？**
- 建议默认：未到达（灰）/ 已到达（蓝）/ 等待 ≥ 8 分钟（红）；阈值可配置；另外增加「即将到达（≤ 5 分钟，黄）」提示员工提前 Prep，这是减少等待时间的关键。
- **答复**：采纳建议默认。

**D-05 [阻塞] 两名员工同时扫描同一订单怎么办？**
- 建议默认：**第一个扫描者获得锁**，订单状态变为 `Prepping(by 员工A)`，所有设备实时刷新；第二个人扫描时提示「A 正在处理，是否请求协助？」——可以加入协助（多人共同 Prep 一个大订单），但不能抢占；锁在 N 分钟无操作后释放；管理员可以强制转移。
- **答复**：采纳建议默认。

**D-06 [重要] 状态机是否完整？**
- 建议默认：`待处理 → Prepping → 待装车（Ready to Load）→ 交付中 → 已完成`，另外有 `部分交付`、`拒收`、`顾客未到`、`异常` 等分支。
- **答复**：采纳建议默认，不需要额外分支。

**D-07 [重要] Delivery 的车内位置（副驾 / 后排 / 尾箱）由谁记录、给谁看？**
- 为什么尖锐：记录的唯一价值是让司机在多单配送时不送错；如果司机看不到这些信息，记录就毫无意义。
- 建议默认：装车员工在系统中选择位置；该信息通过接口推送给司机端；每趟最多订单数可配置（默认 3）。
- **答复**：采纳建议默认；每趟最多可配置为 **4** 单，车内位置为：副驾、后排左、后排右、尾箱。

**D-08 [重要] 停车位编号缺失或输错怎么办？**
- 建议默认：允许员工手动修改；没有车位编号的门店可以关闭此功能，改用车辆描述（颜色、车型）。
- **答复**：采纳建议默认；车位编号优先；没有编号、编号未知或输错时，补充车型和颜色，顾客端和司机端也要提供这些字段。

**D-09 [重要] 顾客早到（订单尚未拣完）怎么办？**
- 建议默认：提示「订单未就绪」，系统给出预计就绪时间，并把该订单的剩余拣货任务提升为最高优先级。
- **答复**：采纳建议默认；同时告知顾客需要更长的等待时间，并说明原因。

**D-10 [重要] HOT / MTO 何时取出？**
- 建议默认：Prep 时最后取 HOT；HOT 区与普通 Staging 分开，有保温设备（≥ 135°F）；系统显示 MTO 的制作完成时间，超时告警；如果采用「以时间作为公共卫生控制」方案，4 小时后强制丢弃。
- **答复**：采纳建议默认。

**D-11 [重要] 交付的服务目标是多少？**
「8 分钟」是告警线，不是服务目标。公开基准：2019 年调查中路边取货平均等待 5 分 21 秒，只有 7% 的订单在 2 分钟内完成；Target 称其约 2 分钟。
- 建议默认：同时追踪「平均等待」和「80% 分位等待」，目标为 80% 分位 ≤ 3 分钟（可配置）；模拟器中用这两个指标对比策略。
- **答复**：采纳建议默认；目标不仅是顾客 / 司机满意，也要避免员工承受过大压力。节假日、购物节等订单激增而人手不足的时段，需要平衡两者。

## L · 标签与二维码

**L-01 [阻塞] 二维码里存什么？**
- 为什么尖锐：如果二维码直接编码顾客姓名或完整订单信息，任何人用手机都能扫出隐私数据。
- 建议默认：二维码只存**不透明标识符**（标签 ID + 校验位），所有信息由系统后台查询；顾客的取货二维码（如有）与框标签使用不同的标识体系。
- **答复**：采纳建议默认。

**L-02 [重要] 顾客姓名显示多少？**
- 建议默认：「姓 + 名首字母」（例如 `ZHANG, W.`），可配置为全名或只显示姓。
- **答复**：显示全名（名 + 姓）；姓名过长时显示「名 + 姓的首字母」。

**L-03 [重要] 标签上的完整字段？**
- 建议默认：二维码、订单短号、框号、`x/n`、温区色块、时段起点、Pickup / Delivery、顾客姓名（缩写）、GMD / HOT 标记、年龄限制标记、打印版本号。**Staging 位置不预印**（事后才确定），只存在系统中。
- **答复**：采纳建议默认；先生成样本图例供参考调整（见 [标签样本](samples/labels.md)）。

**L-04 [重要] 重打标签如何防止重复？**
- 建议默认：每次重打，标签的版本号 +1，旧版本立即作废，扫描旧标签会提示「已作废，请使用新标签」；重打需要记录操作人。
- **答复**：重打通常只是因为标签丢失，不记录操作人；除非是作废已生成的标签，否则版本号不变。

**L-05 [可后定] 冷冻环境的标签材质？**
普通热敏标签的背胶在冷冻环境中可能失效。
- 建议默认：配置中区分「常温标签纸」和「冷冻标签纸」，打印时按温区提示。
- **答复**：不区分标签材质，所有环节统一使用冷冻标签纸。

## X · Exception（后仓取货）

**X-01 [重要] 授权模型？**
- 建议默认：基于角色的权限控制（RBAC），另外支持管理员发放临时授权（带有效期）。
- **答复**：只设永久授权，不需要临时授权。

**X-02 [阻塞] 后仓也找不到（幽灵库存）怎么办？**
- 建议默认：员工点击「后仓未找到」→ 库存标记为可疑 → 自动生成该位置的盘点任务 → 订单走替代或缺货流程。
- **答复**：采纳建议默认。

**X-03 [重要] 取货后的确认信息太多会拖慢速度。**
原始需求的确认项：最新位置、是否还有剩余、是否移动了其他物品到相邻编号。
- 建议默认：全部用**扫描**代替输入：扫描新位置标签 = 确认位置；扫描后点选「空 / 有剩余」；「移动了其他物品」作为可选的二次扫描。目标是 3 次点击以内完成。
- **答复**：采纳建议默认。

**X-04 [重要] Exception 是否应同时补满货架？**
既然货架空了而后仓有货，只取一件给订单就太浪费了。
- 为什么尖锐：这正是把「在线订单」和「货架补货」两个区块连接起来的关键节点，也是整个项目最有说服力的价值点之一。
- 建议默认：Exception 完成后自动生成一条「补货任务」（带建议数量），由补货员接手，或者由同一员工顺手完成。
- **答复**：采纳建议默认。

## I · 后仓库存

**I-01 [重要] 收货时是否核对 ASN / 采购单？**
- 建议默认：扫描托盘标签（SSCC）→ 与 ASN 对比 → 差异（短少 / 多出 / 损坏）生成收货差异记录。
- **答复**：采纳建议默认。

**I-02 [阻塞] 真的需要给每一箱重新打标签吗？**
大多数商品箱上已有供应商条码（GTIN-14 / ITF-14）。重新贴标会增加大量人工。
- 为什么尖锐：如果每箱都要贴标，收货环节的人工可能会抵消后续效率提升。
- 建议默认：**优先复用箱上原有条码**，系统建立「箱码 → 商品 → 箱规（每箱单元数）」的映射；只有在没有条码、条码不可读或拆箱后，才打印内部标签。内部标签采用 GS1 Digital Link 格式的二维码，便于将来与行业标准对齐。
- **答复**：需要。每箱都重新打印**由本地数据库主导**的标签并录入系统，便于数据库管理和 AI 使用。

**I-03 [重要] 存储策略：按类别分区，还是随机存储？**
- 为什么尖锐：随机存储（哪里有空放哪里，系统记录位置）空间利用率更高，但更依赖系统；按类别分区更直观，便于人找。
- 建议默认：两者可配置，默认**「大类分区 + 区内随机」**；强制隔离规则（化学品与食品分开、酒类上锁、高价值商品入笼、冷藏冷冻独立）不受策略影响。
- **答复**：采纳建议默认。

**I-04 [重要] 库存准确率靠什么维持？**
- 建议默认：周期盘点（ABC 分类：A 类每周、B 类每月、C 类每季度）+ 事件触发盘点（Exception 未找到、传感器异常）。
- **答复**：采纳建议默认。

**I-05 [可后定] 退货品、损坏品进入哪个库存状态？**
- 建议默认：可售 / 待检 / 退供应商（RTV）/ 报废四种状态。
- **答复**：采纳建议默认；可售区和报废区都需要再区分常温、冷藏、冷冻。

## R · 货架补货与传感

**R-01 [阻塞] 每个货位都装传感器的成本能否接受？**
调研结论（详见 `02-feasibility.md` 第 4 节）：
- 大型超市约 12 万个商品、15–24 万个货位；逐货位测距的单店资本投入推算为 **50–225 万美元**；
- 价签常用的纽扣电池撑不住：测距仪每分钟测一次就耗尽 5 年的电池预算，**称重方案根本不能用纽扣电池**，必须使用供电导轨；
- 测距只知道「通道还有多深」，**不知道里面是不是正确的商品**；
- 货架传感最多只能直接解决约 **25%** 的缺货（「店里有货但不在货架上」），收益上限约为销售额的 1%；
- 所有主要价签厂商都在做「价签 + 摄像头」（一个摄像头覆盖约 250 个商品），没有一家在做逐货位测距；
- 沃尔玛 2020 年终止 Bossa Nova 货架机器人，亚马逊 2024 年在 Amazon Fresh 撤下 Just Walk Out。
- 建议默认：**混合方案**。
  - 默认用 POS 销售流水推算货架库存（零硬件成本）；
  - 只对**高周转、高缺货率、高价值**的少数品类部署传感器（帕累托原则）；
  - 用员工日常扫描（拣货、补货、Exception）作为被动校准；
  - 系统中的「传感器」是可插拔的数据源，模拟器中全部可仿真。
- **答复**：采用混合方案；交易量低的品类可能不需要部署传感器。

**R-02 [重要] 测距仪（ToF）只适用于特定陈列方式。**
它只适合「单列纵深 + 推进器」的陈列；堆叠、悬挂、散装、形状不规则的商品都测不准；顾客放错位置也会造成误判。
- 建议默认：每个货位记录「陈列方式」，系统据此决定用哪种感知方式（测距 / 称重 / 销售推算 / 视觉）。
- **答复**：采纳建议默认。

**R-03 [重要] 电子价签（ESL）能否承担传感数据回传？**
调研结论：蓝牙 ESL 标准（BLE 5.4）**支持**双向通信和传感器数据收集；但主流厂商的协议（Pricer 红外、SoluM 2.4 GHz、Hanshow HiLPC）是**封闭的**，门店无法自行加装；现实的载体是 VusionGroup EdgeSense 这类**供电导轨**（单根导轨可为最多 25 个设备供电）。沃尔玛目前的价签只用于 LED 指引，**不感知库存**。
- 建议默认：在架构上把「价签网络」和「传感网络」分开定义，传感数据走独立的 MQTT 接入层；价签只负责显示和闪灯指引（例如补货任务派发后，对应货位的价签闪烁）。
- **答复**：采纳建议默认。

**R-06 [重要] 是否做一个桌面级硬件原型？**
- 建议默认：做。一块小货架 + 3–4 个 VL53L1X 测距模块（零售单价约 15–23 美元）+ 一个大米称重位（称重传感器 + HX711）+ 一块开发板，**接市电供电**，通过 MQTT 接入系统，用来证明「可插拔感知层」真实可用。整店规模全部用仿真。
- **答复**：不做实物，但需要详细的材料、步骤等文档，为今后铺垫（见 [货架传感原型指南](hardware/shelf-sensing-prototype.md)）。

**R-04 [阻塞]「根据尺寸重新排布货架」不归门店员工管。**
货架陈列（planogram）通常由总部商品部门制定，还受供应商陈列协议约束。
- 建议默认：系统提供**陈列建议**（基于尺寸和销售速度的建议方案及其依据），而不是自动重排；建议需要人工审批。
- **答复**：采纳建议默认。

**R-05 [重要] 补货请求按什么排序？**
原始需求是「按照时间进行排序」。仅按时间排序会让快卖完的爆款排在慢动销商品后面。
- 建议默认：按**预计售罄时间**排序，并加权考虑销售速度、利润、在线订单需求（已有在线订单占用的商品优先）；同一区域的任务合并成补货批次。
- **答复**：采纳建议默认。

## AS · 替代推荐

**AS-01 [阻塞] 真的需要大语言模型（LLM）吗？**
- 为什么尖锐：拣货场景需要毫秒级响应，可解释、可审计。「属性过滤 + 相似度排序 + 学习历史接受率」比 LLM 更快、更准、更便宜。
- 建议默认：
  - **在线推荐**：规则过滤 + 属性相似度 + 学习排序，延迟 < 50 ms；
  - **离线**：用小型本地 LLM 给商品**补充属性**（口味、用途、饮食标签），这是 LLM 真正擅长的；
  - 推荐理由要能展示给员工（例如「同品牌 · 同口味 · 规格更大」）。
- **答复**：采纳建议默认。

**AS-02 [阻塞] 硬约束清单？**
- 建议默认（不可违反）：顾客的「不允许替代」设置；同温区（新鲜不能换冷冻）；过敏原和饮食属性不能降级（无麸质、有机、素食、清真 / 犹太洁食）；年龄限制属性一致。
  软约束（加权）：同品牌、同口味、规格接近、价格接近、离拣货员近。
- **答复**：采纳建议默认。

**AS-03 [重要] 「离拣货员近」怎么知道拣货员在哪？**
- 为什么尖锐：室内实时定位需要额外的硬件（UWB / BLE 信标），而且涉及员工监控法规。
- 建议默认：用**最近一次扫描的货架位置**作为近似位置，不需要额外硬件，也不需要持续追踪员工。
- **答复**：采纳建议默认。

**AS-04 [重要] 替代品的价格差谁承担？**
- 建议默认：价格策略可配置（按原价 / 按较低价 / 按实际价）。默认：替代品更贵时按原价收费。
- **答复**：默认按替代品的**实际价格**计算。

**AS-05 [可后定] 冷启动？**
没有历史接受数据时怎么排序？
- 建议默认：先用纯属性相似度；有数据后切换为学习排序；模拟器中模拟顾客的接受行为。
- **答复**：采纳建议默认。

**AS-06 [重要] 是否做「预防替代」？**
比起缺货后再找替代，更有价值的是**减少缺货订单的产生**。Instacart 每 60 分钟为约 25,000 家门店的 5 亿多个商品重新计算可售概率；Ocado 通过只承诺可售库存做到「几乎没有替代」。
- 建议默认：根据拣货员的「找到 / 没找到」扫描记录，实时更新每个商品的**可售概率**，通过接口提供给订单平台（低于阈值时前端可以标记「可能缺货」或不再售卖）。
- **答复**：采纳建议默认。

## IP · 包裹

**IP-01 [阻塞] 「IP」是什么的缩写？业务边界在哪里？**
- **答复**：作者推测可能是 Intellectual Property。决议：该含义与包裹业务不符，按中性命名原则，本模块统一命名为 **Parcel Hub（包裹中转）**，见决策记录 0001。

**IP-02 [重要] ASN 由谁发送？Trip（路线）由谁规划？**

**IP-04 [重要] 司机「扫描 ASN 确认接收」用的是谁的 app？**

- **答复**：接入已有的司机端应用（本系统提供接口）。

## W · AI 人员调配

**W-01 [阻塞] 目标函数是什么？**
「最少迟到订单」「最短顾客等待」「最低人工成本」三者互相冲突。
- 建议默认：分层目标——
  1. 硬约束：食品安全时限、法定休息；
  2. 第一目标：迟到订单数最少；
  3. 第二目标：顾客等待超时最少；
  4. 第三目标：调动次数最少。
  权重可由管理员调整。
- **答复**：采纳建议默认。

**W-02 [阻塞] 工作量的单位是什么？**
订单数是一个糟糕的单位：1 单 5 件和 1 单 80 件，工作量差了十几倍。
- 建议默认：以**商品件数、拣货行数、温区数、大件数**估算「标准工时」，而不是订单数。
- **答复**：采纳建议默认。

**W-03 [阻塞] 调动是「建议」还是「强制」？**
- 建议默认：AI 生成调动建议 → 管理员可以一键批准，或设为「自动执行」模式；员工设备收到调动通知后，**完成当前任务**（例如当前推车）再切换；每位员工有最短停留时间（默认 30 分钟），防止频繁调动。
- **答复**：采纳建议默认。

**W-04 [重要] 管理员锁定的优先级与有效期？**
- 建议默认：管理员可以把员工「锁定」在某个区块，可设置有效期（本小时 / 本班次 / 永久名单）；锁定的员工 AI 不能调动；「固定名单」和「可调动名单」由管理员配置。
- **答复**：采纳建议默认。

**W-05 [重要] 员工技能与资质约束？**
Exception 授权、叉车资质、酒类处理的年龄限制（部分州对未成年员工处理酒类有限制）、熟食区食品处理证。另外，联邦童工规定：**14–15 岁员工不得在冷冻库和肉类冷库内作业**（短暂进入取物除外），**18 岁以下不得操作叉车、打包机、压缩机**。
- 建议默认：员工档案包含技能标签和年龄段（只存年龄段，不存生日），调度时作为硬约束；例如未成年员工不会被分配到冷冻暂存。
- **答复**：采纳建议默认。

**W-06 [重要] 法规与员工接受度？**
算法管理、生产率配额披露、员工监控等法规（研究结论见 02 文档）。
- 建议默认：系统**不对个人做排名式展示**，个人效率数据仅本人和管理员可见；所有 AI 调动都有可读的理由；保留完整的审计日志。
- **答复**：采纳建议默认。

**W-07 [可后定] 冷启动？**
没有历史数据时怎么预测？
- 建议默认：先用排队论和规则（例如 Erlang-C 估算交付窗口所需人数），积累数据后再用机器学习预测。
- **答复**：采纳建议默认。

## RT · 退货

**RT-01 [阻塞] 「司机退货」实际上是两种业务。**
① 送达失败 / 顾客拒收 → 整单退回门店；② 顾客发起的上门取件退货。两者的验证、库存处理、退款逻辑都不同。
- 建议默认：拆为「配送退回」和「顾客退货」两条流程。
- **答复**：采纳建议默认。

**RT-02 [重要] 退回商品能否再售？**
- 建议默认：冷藏、冷冻、熟食一律不可再售（报废）；常温食品只有未开封、包装完好才能回架；百货检验后分流（可售 / RTV / 报废）；**危险品（漂白剂、杀虫剂、气雾剂）走专用回收流程，禁止按普通垃圾处理**——沃尔玛曾在 2013 年因不当处理退回的危险品支付约 8,160 万美元。规则可配置。
- **答复**：采纳建议默认。

**RT-03 [重要] 防欺诈？**
扫描的条码与原订单的商品相同，不代表是同一件商品（例如用旧机换新机）。
- 建议默认：高价值商品（电子产品）需要扫描序列号，并与出库记录比对。
- **答复**：采纳建议默认。

**RT-04 [重要] 退款边界？**
- 建议默认：本系统**只发出「退货成功」事件**，不处理任何支付或退款逻辑；退款由外部系统完成。
- **答复**：采纳建议默认。

**C-02 [阻塞] 定制化的方式？**

**C-03 [重要] 配置的版本与生效？**
高峰期修改布局可能让正在进行的作业出错。
- 建议默认：配置有版本号；可以预约生效时间；修改前先在模拟器中试运行（「先仿真后上线」）。
- **答复**：采纳建议默认。

**C-04 [重要] 是否支持多店？**
- 建议默认：数据模型从第一天起就支持多店（`store_id` 贯穿全部数据），但 MVP 只演示单店 + 模板切换。
- **答复**：采纳建议默认。

## V · 模拟器与可视化

**V-01 [阻塞] 模拟器是「仿真器」还是「实时运营系统」？**
原始需求是「真正能够使用的实时检测、管理的可视化运营系统」。
- 建议默认：**同一个前端，三种数据源模式**：
  - **Simulation**：浏览器内仿真，可以加速、暂停、改参数，用于演示和效益对比；
  - **Live**：连接真实后端，展示实时作业；
  - **Replay**：回放历史事件流，用于复盘。
- **答复**：采纳建议默认；预期效果像操作一款**模拟经营游戏**。

**V-02 [重要] 2.5D 风格的参考？**
- 建议默认：等距视角（正交相机）、低多边形、扁平配色、温区用颜色编码（常温米色、冷藏蓝、冷冻青、熟食橙）；员工用简化小人表示；货架剩余量用颜色条或热力图表示。视觉参考由作者提供（游戏或产品）。
- **答复**：采纳建议默认；门店可能有二层或其他结构，因此 2.5D 与 3D 都需要，且视角可切换；视觉风格可参考风格化开放世界游戏和城市建造类游戏的氛围，但保持简单简洁（这不是正统游戏）。

**V-03 [重要] 在模拟器里能「操作」到什么程度？**
「直观查看并操作所有细则」——是能在 3D 场景里点击货架补货、拖动员工改派，还是只能看、在面板中操作？
- 建议默认：场景中可以点选任何对象查看详情；改派员工、调整规则、触发事件（例如「突然来了 30 单」「冷柜故障」）在侧边面板中操作；布局编辑在编辑模式中拖拽完成。
- **答复**：默认方案可行；最好再加上在 3D 场景中**直接点击货架补货、拖动员工改派**等操作。

**V-04 [重要] 需要支持哪些设备？**
- 建议默认：桌面浏览器为主；平板可用；手机上提供简化的 2D 视图。
- **答复**：采纳建议默认。

## E · 效益对比

**E-01 [阻塞] 基线数据从哪里来？**
不能使用任何零售商的非公开数据。
- 建议默认：
  1. **公开行业数据**（学术文献、行业报告，注明来源）；
  2. **仿真对比**：同一门店配置、同一订单流（相同随机种子）、两套策略（「现状通用做法」vs「本系统策略」），多次重复运行后给出置信区间；
  3. 作者的观察与合理推测只用作参数范围，并明确标注。
  所有结论都附上假设和敏感性分析。
- **答复**：采纳建议默认。

**E-02 [重要] 指标体系？**
- 建议默认：
  - **拣货**：每小时拣货件数（UPH）、行走距离、缺货率（INF）、替代率与替代接受率；
  - **暂存**：入位时间、找框时间、占用率峰值；
  - **交付**：顾客平均等待、超过 8 分钟比例、准时率；
  - **库存**：货架缺货率、补货响应时间、库存准确率；
  - **人员**：人均订单件数、调动次数、空闲率；
  - **财务**：单均履约成本、缺货导致的销售损失、人工节约。
- **答复**：采纳建议默认。

**E-03 [重要] 收益换算口径？**
- 建议默认：人工节约（节约工时 × 时薪，可配置）+ 缺货减少带来的销售挽回（用公开研究的缺货损失比例，做敏感性分析）+ 等待时间缩短对复购的影响（只做定性说明，不编造数字）。
- **答复**：采纳建议默认；结合行业通用做法、公开数据、上市公司财报等综合判断。
