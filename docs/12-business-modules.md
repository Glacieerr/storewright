## 1. 一页结论

- **四个扩展模块都可以在门店配置里单独开关**：熟食现做、退货、大件（先扫后打）、包裹中转。关闭时相关命令被拒绝（`MODULE_DISABLED`），员工端不显示对应页面。每个模块有自己的状态、命令、事件和排程，核心代码不需要知道有哪些模块。
- **每个模块有一个 AI 接入点**，与 Phase 5 的建议记录、采纳统计、模型仓库和上线门槛打通：熟食开始时间（默认自动执行）、退货去向建议（员工决定，是否采纳计入统计）、大件装载规划、包裹格位建议。
- **同一套核心做了第二个行业：家居建材店**。改的是配置和数据（品类、布局、需求形态、合成商品），以及两处在超市里被当成默认的假设。领域模型、规则引擎、分框分批、仿真引擎、作业核心、员工端和 AI 框架都直接复用，Phase 1 的超市结果逐字节不变。
- **迁移本身得到的结论**：同一套功能在两个行业里，回报来自不同的地方。

| | 中型超市 | 家居建材店 |
|---|---|---|
| 主要收益 | 安全（超重、压坏、化学品混装）、等待时间、门口停留 | 安全（**17.6% 的框超重**，降到 0）、门口停留、满足率 |
| 分批与路线 | 有用（每单 18 行，多单合并一车） | 几乎没用（每单 5 行，每单约 1 框） |
| 后仓补取 | 挽回缺货，工时增加 | 同样，满足率提升更大（+1.4 个百分点） |
| AI 排班 | 平均等待 −0.44 分钟 | **90 分位等待 −9.7 分钟、迟到订单 9.9% → 约 0%**（早上施工队高峰明显） |
| 退货去向模型 | 比固定规则正确率 +1.1 个百分点 | 与规则相同，上线门槛保留规则 |

这正是接入方法论要回答的问题：**先用本店配置和需求形态跑一遍仿真，再决定打开哪些功能**，而不是把一个行业的「最佳实践」整套搬过去。

## 2. 模块框架

代码在 `packages/ops/src/modules/`。每个模块是一个对象：

```ts
interface OpsModule {
  id: 'mto' | 'returns' | 'oversized' | 'parcel';
  commands: ReadonlySet<OpsCommandType>;           // 这个模块处理哪些命令
  decide(state, envelope, ctx): Decision;         // 校验命令、产生事件（纯函数）
  apply(state, event, statics?): boolean;          // 把事件应用到状态（只改自己那一块）
  tick?(state, at): PendingEvent[];                // 排程：保温超时、包裹短少等
}
```

- `decide` 收到命令时先查模块注册表；命令属于某个模块且门店没有启用该模块，直接拒绝 `MODULE_DISABLED`。
- `applyEvent` 依次交给各模块，返回 `true` 表示已处理；`Tick` 最后一步调用各模块的 `tick`。
- 状态里每个模块一块（`mto`、`returns`、`oversized`、`parcels`），回放事件日志得到完全相同的状态（测试覆盖）。
- 门店静态数据里有模块开关和模块需要的配置：熟食菜单与保温位、包裹格位（S / M / L 和容量）、大件区。
- 新增一个模块 = 新增一个文件并在注册表里登记一行，加上命令、事件类型和员工端页面。

## 3. 四个模块

### 3.1 熟食现做

| 环节 | 规则 |
|---|---|
| 建单 | 订单含现做商品时建现做单；建议开始时间 = 时段起点 − 制作时长 − 缓冲 10 分钟 |
| 制作 | 排队中按建议开始时间排序，晚了标红；开始制作 → 完成并放入保温位 |
| 保温 | 完成后开始计时，超过保温时限由排程自动丢弃（记录原因）；订单取消时未取出的现做单一并丢弃 |
| 取出 | 交付准备时最后取热食 |
| **AI** | 按菜品在本店的实际系数和厨房当时的负荷预测制作时长，调整建议开始时间；默认「自动执行」（只改变看板上的提醒时间，看板标出「AI 调整」和标准时间） |

离线评估（3 个种子）：按标准时长估计的平均误差 6.4–7.3 分钟，菜品系数 + 负荷模型 **1.8 分钟**。

### 3.2 退货

| 环节 | 规则 |
|---|---|
| 开单 | 顾客退货（可以关联原订单，也可以无小票）或配送退回 |
| 逐件 | 选择状态（未开封 / 已开封 / 损坏）和数量后扫码；不在原订单里的商品标出来 |
| 去向 | 可售回架（货架估算增加，等下次扫描确认）、报废、危险品回收、退供应商 |
| **硬性规则**（决策 RT-02） | 冷藏、冷冻、热食一律不能回架；超市的散件（食品、日用品、个护）只有未开封才能回架；损坏的不能回架；化学品不能按普通垃圾报废，开封或损坏的化学品只能走危险品回收。被禁止的去向在界面上不可选并说明原因，命令也会被作业核心拒绝（`DISPOSITION_NOT_ALLOWED`） |
| 完成 | 每件都有去向才能完成；发出「退货完成」事件和退款金额（退款由外部系统处理） |
| **AI** | 每件给出去向建议、能再售的概率和主要理由（例如「已开封 −94%」「冷藏商品离开冷链约 24 小时」），建议只在规则允许的去向里给出（模型给出被禁止的去向时改为允许的去向，并在理由里说明）；员工在允许的去向里选，与建议相同记为采纳，不同记为否决 |

没有原订单时不知道交付了多久，按 24 小时估计，理由里会注明「按 24 小时估计」。

| 门店 | 方法 | 判断正确率 | 误判回架 | 可售却报废 |
|---|---|---|---|---|
| 中型超市 | 固定规则 | 82.3% | 5.5% | 12.2% |
| 中型超市 | 再售概率 + 规则 | **83.4%** | 5.9% | **10.7%** |
| 家居建材店 | 固定规则 | 85.4% | 7.7% | 6.9% |
| 家居建材店 | 再售概率 + 规则 | 85.4% | 7.7% | 6.9% |

超市里模型少报废了 1.5 个百分点的可售商品，代价是误判回架多 0.4 个百分点（上线门槛允许的范围内）；建材店没有易腐和冷链商品，规则已经抓住了主要因素，模型没有带来改进，模型仓库的上线门槛（至少提高 0.2 个百分点）会保留规则。

### 3.3 大件（先扫后打）

| 环节 | 规则 |
|---|---|
| 生成 | 锁单时分框算法分出的大件（单件过重、超出框内径、同品合计过重）按件生成任务；超过 50 lb 的件标为两人搬运 |
| 领取 | 员工领取一单的大件时，这一趟能装几件就领几件，剩下的留给别人 |
| 先扫后打 | 扫描商品条码确认是这件，再打印这一件的标签（与取货框同一版式，显示「PIECE 1/3」） |
| 暂存 | 放到大件区（区域级位置）；交付看板能看到每单的大件进度 |
| **AI** | 装载规划：按重量和是否需要两人搬运把一单的大件分成几趟（重的先放、每趟不超过 25 kg 和 4 件、两人搬运的件单独一趟）；员工可以直接领取「第 1 趟」 |

### 3.4 包裹中转

| 环节 | 规则 |
|---|---|
| 到货通知 | 承运商的通知先到（演示中由控制台发送），列出包裹、行程和尺寸 |
| 入站 | 扫描包裹编码；没有通知的标为「多出（待核实）」 |
| 短少 | 超过预计到货时间 + 30 分钟仍未入站的，由排程标为短少 |
| 暂存 | 放进格位（S / M / L，有容量）；损坏的单独登记 |
| 交接 | 司机按行程整批交接；行程里还有已入站但没暂存的包裹时不能交接 |
| **AI** | 格位建议（规则打分）：同一行程已经在用的格位优先（司机一次取走），其次是尺寸刚好合适、还有空位、离门口近的格位；界面上显示建议和理由 |

## 4. 第二个行业：家居建材店

### 4.1 为什么选它

与超市差别最大：没有冷链和年龄限制；单件重、长件多，大件和多件购买多；订单以少量行为主，大件为主的订单比例高；周六和工作日早上（施工队）是高峰，春季是旺季。能同时检验大件、退货、包裹中转模块，以及仿真引擎和 AI 预测在另一种需求形态上的表现。

### 4.2 改了什么、复用了什么

| 层 | 家居建材店做了什么 | 性质 |
|---|---|---|
| 门店配置 schema | 加了一个可选字段 `industry`（没有时视为超市）和模板名 `hardware` | 新增（向后兼容） |
| 门店生成器 | 行业参数选择品类字典、通道顺序、沿墙货架（板材墙、建材、家电）、暂存区（没有冷藏 / 冷冻 / 热食货架，大件区 8 格）、默认模块（打开包裹中转）、营业时间 6:00–21:00 | 参数化 |
| 品类与合成商品 | 17 个品类、67 个商品原型（紧固件、工具、水暖、电工、油漆、板材、建材、家电、户外动力设备……） | 新增数据 |
| 需求场景 | 每天约 150 单、每单约 5 行、每行约 2 件，早上 7–9 点是高峰，自取 72%，大件为主的订单 28% | 新增数据 |
| 需求历史（AI 训练用） | 行业需求形态：星期（周六 ×1.45）、节假日（阵亡将士纪念日和劳动节是旺日，圣诞节几乎没有生意）、天气（大雨推迟户外工程，风暴预警前一天抢购）、季节性（5 月初是峰值，振幅 20%，隐藏因素）、周末的小时分布 | 参数化 |
| 后仓 | 分区按行业（五金 / 工具 / 板材建材 / 大件 / 化学品），没有冷库 | 参数化 |
| 陈列 | 五金和手动工具挂洞洞板，板材和建材按堆放 | 参数化 |
| 排班与毛利 | 按与超市相同的口径校准排班（见 4.3），毛利 33% | 参数化 |
| 演示门店 | `STORES=demo,hardware` 同一个服务同时运行两个门店；建材店没有熟食员工和熟食模块 | 参数化 |
| 领域模型、规则引擎、分框分批、路线、仿真引擎、作业核心、事件溯源、员工端、标签、AI 框架与模型 | 不改，直接复用；AI 模型用本店的合成历史重新训练 | 复用 |

**两处在超市里被当成默认的假设**，迁移时才暴露出来：

1. **「化学品与食品分开装框」**：原来把所有门店拣货的散件都当成食品，建材店的油漆就会单独占一个框，「化学品与食品混装」指标也会误报 45%。现在商品可以标记为非食品（只有建材店的商品带这个标记），超市的行为和结果不变。
2. **订单类型的名字**：领域模型里门店拣货的散件订单叫 `GROCERY`。建材店沿用这个类型（含义是「拣进取货框的散件」），没有改名，避免牵动所有模块；这是一处命名上的技术债，记录在这里。

### 4.3 排班校准

按超市的口径：基线策略下拣货利用率约 57%（超市约 67%，建材店早高峰更集中），平均等待约 4–5 分钟，每个岗位每小时至少 1 人。第一次直接按订单量缩放时总排班 134 小时、实际作业只有 28 小时，等待短得不真实；校准后 93 小时。

**订单量预测**（730 天合成历史，最后 365 天按周滚动回测，按小时 WAPE）

| 预测器 | 中型超市 | 家居建材店 |
|---|---|---|
| 同时段上周值 | 25.9% | 33.2% |
| 近 4 周同时段平均 | 20.5% | 26.5% |
| 季节性指数平滑 | 19.3% | 24.9% |
| 已知因素回归 | **18.5%** | **23.8%** |

同一套预测器和特征，只换数据：已知因素回归在两个行业里都是最好的，与理论下限的差距分别是 1.8 和 2.2 个百分点。建材店每小时只有几单，泊松噪声占比更大，下限本身更高；季节性是模型看不到的因素，由局部水平跟上。

## 5. 员工端与演示

- 员工端新增「扩展」页（门店启用了扩展模块才显示），按岗位默认打开对应模块：熟食员工看熟食看板，后仓看包裹，交付看退货，暂存看大件。每个模块都有「点选代替扫描」的演示入口。
- 控制台：下单时可以勾选「每单加一份熟食现做」「每单加一件大件」；包裹中转卡片发送到货通知、查看各行程、代替司机交接。
- AI 页的模型列表新增「熟食制作时长模型」「退货去向模型」，建议列表能看到熟食开始时间的建议与理由。
- 运行两个门店：`STORES=demo,hardware npm run server`，登录页的门店填 `hardware`。模拟器的模板下拉框里可以选「家居建材店」。

## 6. 简化与尚未完成的部分

- 外部系统（订单平台、承运商、POS、退款）都由控制台代替；退款只发出事件。
- 熟食只有现做单和保温，没有食材库存与配方；包裹格位建议是规则打分，不是学习模型。
- 退货的再售与否由合成数据生成，建材店里与规则所用的因素重合，所以模型没有改进；真实数据里（例如开封的电动工具能否翻新）可能不同。
- 建材店的 AI 误差大小沿用超市的设定；仿真里的大件只计件数和搬运时间，没有模拟叉车装车。
- 订单类型 `GROCERY` 的命名债（见 4.2）。
