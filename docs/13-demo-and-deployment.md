## 1. 一页结论

- **整个系统可以在浏览器里运行，不需要后端**：员工端的演示构建把门店中枢（命令处理、事件日志、排程、门店 AI 服务、本地助手）放进一个 SharedWorker；同一个网站打开的所有标签页和 iframe 共用一家店，实时同步；数据保存在浏览器的 IndexedDB 里，关掉再打开门店还在。只需要静态托管。不支持 SharedWorker 的浏览器每个页面用一个专用 Worker：展示页里的几个画面照样共用一家店、照样保存，多个标签页之间不共用时页面上会说明（决策记录 0015）。
- **演示网页和本地后端跑的是同一份代码**：服务端的全部接口逻辑抽成了与传输方式无关的门店中枢（`apps/server/src/hub.ts`），Fastify 只是外壳；浏览器里的中枢换成内存存储和纯 TypeScript 的 SHA-256。
- **展示页**：左边是三维数字孪生和演示控制台，右边是两部员工手机，全部连到同一个中枢。上方的 7 步引导按门店的实时状态自动打勾（下单 → 拣货 → 暂存 → 到店 → 交付 → AI → 孪生，决策记录 0016）；手机上一次显示一个画面，用标签切换。
- **多浏览器端到端测试代替真机验收**：真实后端 4 个、浏览器内演示 16 个（含展示页里两部手机的真实点击、在岗人员与调配、准备中取消订单，`e2e/phones.demo.spec.ts`）、无障碍 3 个场景，在 Chromium、WebKit（Safari 内核）、Firefox、不支持 SharedWorker 的浏览器、iPhone 和安卓手机上运行，共 83 个（决策记录 0015、0016、0024、0025）；本机用已安装的 Chrome，持续集成用 Playwright 自带的浏览器。
- **持续集成与部署配置已写好，没有执行部署**：GitHub Actions（类型检查、全部测试、Phase 1 对比实验、全部浏览器的端到端测试）；演示站点的 GitHub Pages 工作流只能手动触发；后端的 Dockerfile。

## 2. 门店中枢：同一份代码，两种运行方式

```
              ┌──────────────── apps/server/src/hub.ts（与传输无关） ────────────────┐
              │ 路由表 · 会话 · 命令校验与权限 · 演示接口 · 标签 · AI 接口 · 排程      │
              │ StoreRuntime（事件溯源）· AiService · Assistant · StoreSim            │
              └───────▲───────────────────────────────────────────▲─────────────────┘
                      │ HubStorage / HubPlatform                   │
     ┌────────────────┴──────────────┐            ┌────────────────┴──────────────────┐
     │ 本地后端（Node）               │            │ 浏览器内演示（SharedWorker）        │
     │ Fastify 外壳 app.ts            │            │ src/demo/hubWorker.ts             │
     │ SQL 存储（PGlite / PostgreSQL） │            │ 内存存储 memoryStorage()          │
     │ node:crypto                    │            │ Web Crypto 随机数 + TS SHA-256     │
     │ WebSocket、静态文件、MQTT       │            │ MessagePort 消息                  │
     └───────────────────────────────┘            └───────────────────────────────────┘
```

| 抽象 | 作用 | 服务端实现 | 浏览器实现 |
|---|---|---|---|
| `HubStorage` | 事件日志（乐观并发）、元数据、会话、AI 模型仓库 | `sqlStorage(db)`（`eventStore.ts`） | `memoryStorage()`（`storage.ts`） |
| `HubPlatform` | SHA-256、安全随机数 | `nodePlatform`（`platform.node.ts`） | `webPlatform`（`platform.ts`，与 Node 结果一致，有测试） |
| `Hub.handle(req)` | 一次请求 → 状态码 + 内容 | Fastify 把 `/api/*` 转过来 | 页面的 fetch 替身经端口转过来 |
| `Hub.connect(...)` | 实时连接：hello、快照或补发、推送 | WebSocket | WebSocket 替身经端口转过来 |

`hub.ts`、`storage.ts`、`platform.ts` 不能引用 Node 专有的模块（MQTT 桥接拆到 `mqttBridge.ts`，只有服务端外壳引用）。服务端的 30 个接口测试在重构后全部通过。

## 3. 浏览器里的连接

- **SharedWorker**：名字固定（`storewright-demo-hub`），同一个网站的所有页面连到同一个实例。第一次用到某家店时建店，并用本店配置的仿真历史训练 AI 模型（几秒，界面显示提示）；之后每 15 秒一次排程，每分钟生成拣货批次。
- **页面这一侧**（`src/demo/transport.ts`、`packages/ops/src/hubLink.ts`）：演示模式下，页面里所有 `/api/` 请求转给中枢，`LiveClient` 改用 WebSocket 替身，其余代码不用改。
- **标签**：没有服务器可以打开 `/api/.../labels/...`，演示模式下标签链接改为 `label.html#原地址`，标签页面向中枢取 SVG 或 HTML。
- **模拟器**：模拟器是另一个应用，它在隐藏的 iframe 里打开员工端的 `bridge.html`，向它要一个连到同一个中枢的端口（中枢可以接收额外的端口），然后用同样的替身连接，场景切到「只显示实时数据」。
- **不支持 SharedWorker 的浏览器**（例如安卓上的 Chrome）：员工端在本页开一个专用 Worker；展示页里的 iframe 向展示页要端口，几部手机和数字孪生画面仍然共用一家店（决策记录 0015）；单独打开的模拟器页面没有展示页可问，用自己的门店。
- **数据**：中枢在内存里读写，同时按顺序写入 IndexedDB（`src/demo/idbStorage.ts`）；中枢启动时恢复，刷新或关闭所有页面后再打开，门店还在。超过 12 小时没有写入时清空作业事件（保留 AI 模型和验证码的盐），避免打开一家订单全都过期的店。展示页的「重置演示门店」和控制台的「清空门店」清空作业数据。只有 SharedWorker 会写入；退回专用 Worker 时只放内存（几个 Worker 同时写会互相覆盖）。

| 地址 | 作用 |
|---|---|

## 6. 持续集成（`.github/workflows/ci.yml`）

运行环境固定为 Ubuntu 24.04（`ubuntu-latest` 从 2026 年 10 月起逐步换成 26.04，字体和浏览器依赖会跟着变）。

- `check`：`npm ci` → 类型检查（4 个工程，含端到端测试代码）→ 全部单元与属性测试 → Phase 1 对比实验能运行；
- `e2e`：同样的 83 个用例按浏览器分成 4 个并行任务（Chromium 23 个；不支持 SharedWorker 的浏览器和安卓 18 个；WebKit 和 iPhone 22 个；Firefox 20 个），每个任务构建全部应用、只安装自己用的浏览器，失败时上传报告。持续集成里等待上限是 30 秒（本机 15 秒），失败的用例再跑一次、报告里标成 flaky（不稳定），trace 只在重跑时录（录屏和页面快照很耗 CPU）；每个任务最长 45 分钟。

持续集成的机器没有显卡：Chromium 用 SwiftShader、WebKit 用 llvmpipe 在 CPU 上软件渲染 WebGL，Firefox 没有 WebGL。

第一次在 GitHub 上运行（2026-10-29）有 11 个失败，本机全部通过。原因和修改：

- **软件渲染拖慢整页**：三维场景默认高画质（阴影、后期处理），软件渲染时一帧要好几秒；展示页里控制台、手机和三维孪生在同一个页面，每次点击都要等 10 秒以上，几个用例超时。模拟器现在读 WebGL 的渲染器名称，软件渲染时默认低画质（`apps/simulator/src/scene/softwareGl.ts`，顶栏仍可以改）。本机用 `PW_SOFTWARE_GL=1 npm run e2e` 可以复现（Chrome 关掉显卡加速、软件渲染）：「你的商店」用例从 1.2 分钟降到 32 秒，每次点击从 4～5 秒降到 2 秒以内。
- **Firefox 没有 WebGL**：三维场景显示「三维场景出错：Error creating WebGL context.」，孪生用例等不到设备牌。场景现在直接说明「这个浏览器现在不能显示三维场景（WebGL 不可用……）」；孪生用例在没有 WebGL 的浏览器里跳过三维设备牌（报告里有注记），告警、手机、时间轴和孪生面板照常检查。
- **测试本身的时序**：机器慢时，逐框暂存的上一个框还没从列表里消失就去点下一个；取消订单的用例在「取出框」生效之前就取消了订单。改为每一步等结果出现再继续（应用本身没有问题）。
- **字体行高**：Linux 上字体的行高高一点，手机宽度模拟器的顶栏是 60.6 像素，超过了「小于 60 像素」的判断。改为检查顶栏里的控件在同一行。

修这些问题时，本机又发现一个和时间有关的问题（换个时间在持续集成里跑也会遇到）：AI 用例按「接下来」三个字找订单量预测的卡片，下午积压时排在前面的运营预警，理由里也有「接下来 2 小时还会来约 N 单」，用例在这张卡片上找不到「有用」。改为按标题「接下来 N 小时的订单量」找，并检查这次多采纳了一条；以前同一个后端上 Chrome 先采纳过一条，WebKit、Firefox 上这一步等于没有检查。

第二次运行全部通过，但端到端测试一个任务跑了 58.5 分钟（当时的上限是 60 分钟），2 个用例重跑后才通过：拣货流程里「等框离开待暂存」用了默认的 15 秒；孪生用例的「已确认，正在处理」在告警条收起之前同时出现在顶部和下面一行「Taylor 已确认，正在处理」，按文字找到两处。于是改成上面的 4 个并行任务，等门店中枢处理的地方给 60 秒，确认后看告警条顶部的文字。本机按持续集成的条件（软件渲染、`CI=true`）复查时又找到一处：交付时输入取货码点「核验」后，测试马上判断要不要核验证件，机器慢时「已核验证件」还没出现就判断成不用，「完成交付」一直不能点（只在订单里随机有年龄限制商品时出现，第一次运行的失败里也有它）。改为先等「完成交付」出现（它和年龄核验一起出现）再判断；走查的送货部分同样修改。还有一处是 trace 掩盖的：改成只在重跑时录 trace 以后，第一次运行的每一步快了一点，拣货流程点完「开始准备」马上数准备清单，清单还没渲染出来就数成 0，一个框也不取，「完成交付」一直不出现（本机录 trace 时碰不到）。改为先等清单出来。之后在本机按持续集成的设置（不录 trace、不重跑）复查：全部 83 个用 GPU 跑一遍，Chromium 的 41 个再用软件渲染跑一遍，全部通过。

## 7. 部署

**演示站点（推荐，纯静态）**

```bash
npm run build:site
```

产物在 `site/`（`app/`、`sim/`、`index.html`），所有路径都是相对的，可以放到任意静态托管的任意子路径：

| 托管 | 做法 |
|---|---|
| GitHub Pages | 仓库 Settings → Pages 选择 GitHub Actions；Actions → Deploy demo site → Run workflow（`.github/workflows/pages.yml`，只能手动触发） |
| Cloudflare Pages / Netlify / Vercel | 构建命令 `npm run build:site`，输出目录 `site`，Node 22 |
| 个人网站的子路径或子域名 | 把 `site/` 的内容上传到对应目录 |

本地预览：`npm run demo:site`（http://127.0.0.1:4177/ ，需要先构建）。

**实时后端（自托管）**

```bash
docker build -t storewright .
```

```bash
docker run -p 8787:8787 -v storewright-data:/data storewright
```

非演示部署设置 `DEMO=0` 和 `CONSOLE_KEY`；手机摄像头扫码需要 HTTPS（反向代理，或 `HTTPS=1` 用本地自签名证书）；`DATABASE_URL` 指向 PostgreSQL 时不用嵌入式数据库；`STORES=demo,hardware` 同时运行两个门店；本地语言模型见 [门店 AI](10-store-ai.md)。
