# 决策记录 0008 · Phase 3 计划：员工作业端与实时后端

> 日期：2026-10-20 · 状态：已采纳，3a–3f 已完成（结果见 [实时作业](../08-live-operations.md)）
> 范围来自 [评估与路线图](../05-evaluation-and-roadmap.md) Phase 3；工作流来自 [工作流设计](../01-workflow-design.md) 第 3、4.1、4.2、4.6、4.7、5、6 节；技术栈来自 [技术栈](../04-tech-stack.md) 3.3–3.5 节。

## 1. 目标与验收

- 一张测试订单走完全链路：下单 → 锁单 → 分框 → 生成拣货批次 → 打印标签 → 领车拣货 → 暂存 → 顾客签到 → 准备（加锁）→ 核验验证码 → 交付完成。
- 两台手机 + 一台电脑同时操作，状态同步 p95 < 200 ms（命令提交到其他设备收到事件）。
- 断线重连后自动补齐错过的事件；离线时扫描的操作在恢复连接后提交，由服务端校验。

## 3. 关键设计

### 3.1 事件溯源：同一套纯函数在三处运行

- `decide(state, command, ctx) → events | 拒绝原因`，`evolve(state, event) → state`，全部是纯函数，放在公开的 `packages/ops`。
- 服务端用它校验命令、产生事件；员工端和模拟器用同一个 `evolve` 把事件流还原成状态，界面直接读状态。规则只写一遍，保证模拟器、后端、员工端一致（技术栈原则 2）。
- 时间由服务端写入命令（`at`，毫秒），随机数（验证码）由服务端生成后放进命令，`decide` 本身不读时钟、不取随机数，可复现、可测试。
- 验证码只以哈希形式进入事件；哈希函数由调用方注入。

### 3.2 存储：PostgreSQL 方言，默认用嵌入式 PGlite

- 事件表 `events(store_id, seq, at, type, payload jsonb)`，主键 `(store_id, seq)`。追加时按「期望版本」写入，主键冲突即并发冲突，重新读取状态后重试（乐观并发，技术栈 3.3 节）。同一进程内再按门店串行处理命令，避免不必要的冲突。
- 默认使用 **PGlite**（编译成 WebAssembly 的 PostgreSQL，作为普通 npm 依赖运行在 Node 进程里，数据存在本地目录），不需要安装数据库；设置 `DATABASE_URL` 时改用真正的 PostgreSQL（`pg` 驱动）。两者执行同一份 SQL。
- 当前状态保存在内存中，启动时由事件重放得到；以后事件量大时再加快照表。

### 3.3 实时推送：快照 + 流序号 + 断线重同步

- 客户端连接 WebSocket 时带上自己最后收到的序号；服务端补发之后的事件，差得太多时直接发快照。
- 每条事件带门店内单调递增的序号；客户端发现序号不连续就请求补发。
- 命令走 REST（`POST /api/commands`），返回产生的事件；同一批事件同时推送给所有订阅者。
- 传输层抽象为接口：Phase 3 实现单进程内的广播；云端演示形态（托管实时广播）和自托管多实例（NATS JetStream）以后作为同一接口的其他实现。

### 3.4 员工作业端

- React + Vite 的 PWA，手机优先，大按钮、高对比度、单手操作；中英文界面。
- 扫码层抽象为接口：摄像头（浏览器的 BarcodeDetector，不支持时用 jsQR 解码二维码）、硬件扫码枪（模拟键盘输入 + 回车）、手动输入。
- 身份：演示阶段从员工名单中选择身份，服务端发放会话令牌，不使用密码；正式的登录和权限在商业化前接入。
- 离线：命令先进入本地发件箱，恢复连接后按顺序提交；服务端拒绝的命令在界面上提示原因（例如锁单冲突以服务端为准）。完整的离线同步（PowerSync）留到真实设备阶段。

### 3.5 演示数据

- 门店用中型模板，商品目录和订单用合成数据（`packages/synth`）生成，姓名、商品都是虚构的。
- 演示控制台：创建测试订单、立即锁单、生成拣货批次、模拟顾客「我在路上」和到店签到。

- Exception 的执行流程、后仓库存、补货（Phase 4）：Phase 3 中拣货员可以把缺货标记为「转后仓补取」，只生成待办任务。

- 真实扫码设备（Capacitor + DataWedge）与蓝牙打印。

## 6. 实施结果与偏差

- **完成**：3a–3f 全部完成，新增 25 个测试（作业核心 12、标签 4、后端集成 7、员工端界面文字 2），全部测试 119 个通过。同一台电脑上三个客户端的同步延迟 p95 5.4 ms。
- **偏差一：车边不再逐框扫描**。交付时只在从暂存区取出时逐框扫描一次，核验验证码后直接交付；按 G-10 适当简化。
- **偏差二：每个标签页一个身份**。员工端的登录信息先存在标签页（sessionStorage），再存一份到本机（localStorage）供下次打开使用，这样一台电脑可以同时打开几个身份做演示。
- **发现的问题**：
  - 静态文件插件默认只注册启动时已存在的文件，重新构建员工端后新文件名回落到页面，导致白屏；改为按请求查找文件，缺失的静态资源返回 404。
  - PostgreSQL 的 jsonb 会重排对象的键，重启后重放得到的状态与内存状态结构相同但 JSON 文本不同；测试改为按结构比较。
  - 验证码错误也是一条事件（记录尝试次数），界面最初按成功给出反馈；改为识别这条事件按失败处理。
  - 替代品最初只按价格排序，会给牛奶推荐酸奶、推荐同名商品；改为品名相近优先并排除同名商品。
