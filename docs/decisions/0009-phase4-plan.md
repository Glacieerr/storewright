# 决策记录 0009 · Phase 4 计划：后仓库存、Exception、补货

> 日期：2026-10-20 · 状态：已采纳，4a–4f 已完成（结果见 [后仓库存、Exception 与补货](../09-backroom-replenishment.md)）

## 1. 目标与验收

- 验收（路线图）：模拟器中可以看到「货架空 → Exception → 补货任务 → 货架恢复」的完整闭环。
- 同一个闭环在实时系统中也能走通：货架存量估算显示为空（拣货员报告找不到 / 传感器 / 销售推算）→ 授权员工执行 Exception，从后仓箱子取货送到暂存区 → 系统自动生成补货任务（X-04）→ 补货员从后仓取箱、扫描货位上架 → 存量估算恢复并被校准。

## 3. 关键设计

### 3.1 货架存量估算（决策 R-01、R-02、P-06）

- 每个货位有陈列方式（推进器 / 堆叠 / 悬挂 / 散装）和可选的传感器（测距 / 称重）。默认零硬件：只有高周转、高价值的少数货位配传感器。
- 估算值 = 上一次确认值 − 之后的销售与拣货；确认来源按可信度：员工扫描（补货上架、拣货、报告找不到）> 传感器 > 销售推算。置信度随时间和未确认的变动衰减。
- 拣货员报告「找不到」等于确认该货位为空，立刻触发补货判断。
- 估算是事件的纯函数，服务端、员工端、模拟器看到的一致。

### 3.2 补货任务（决策 R-05、X-04）

- 触发：Exception 找到后（建议数量 = 货位容量 − 当前估算）；估算低于阈值或预计售罄时间短于阈值；手动（模拟器点击货架、员工端）。只有后仓有可售库存时才生成。
- 排序：预计售罄时间越短越靠前，并按销售速度、单价、在线订单需求（还没拣的订单行）加权。
- 同一通道的任务合并成一批，补货员一次领取一批。
- 完成：从后仓扫描箱子 → 扫描货位 → 输入上架件数；剩余件数留在箱里放回原库位。上架后的件数作为新的确认值。

### 3.3 后仓库存（决策 I-01～I-05）

- 收货：ASN 先到 → 卡车到店 → 扫描箱上原有条码后自动生成内部箱号，按托盘批量打印内部标签（I-02）→ 关闭收货单时与 ASN 比较，生成短少 / 多出 / 损坏记录。损坏箱进入待检状态。
- 库存状态：可售、待检、退供应商、报废；可售和报废按常温、冷藏、冷冻分区（I-05）。
- 上架：系统建议库位（大类分区 + 区内选最空的库位），员工可以扫描其他库位；温区和隔离规则（化学品与食品分开）始终强制（I-03）。
- 盘点：ABC 分类（A 每周、B 每月、C 每季度）+ 事件触发（Exception 未找到、收货差异、传感器异常）（I-04）。Exception 未找到时把该商品的后仓记录标为可疑并生成盘点任务（X-02）。

### 3.4 Exception（决策 X-01～X-04）

- 只有永久授权的员工可以领取。系统列出有该商品可售箱的库位；扫描箱子 = 确认找到；点选「库位还有 / 已空」；送到订单的框所在的暂存格位并扫描格位确认。目标 3 次点击以内。
- 找到后自动生成补货任务；未找到时订单行保持缺货，后仓记录标为可疑并生成盘点任务。

### 3.5 感知层（决策 R-01、R-03）

- 传感器读数统一成原型指南 7.9 节的 JSON（`storewright.shelf-sensing/0.1`）。后端提供 HTTP 入口；设置 `MQTT_URL` 时订阅 `storewright/v1/{store}/sense/+/+/+/state`。两种入口进入同一个转换函数。
- 读数只有在件数变化、置信度明显变化或超过心跳间隔时才写成事件，避免事件流被心跳淹没。读数超出容量或跳变异常时标记传感器异常。
- 仿真：后端可以按商品热度和时段生成销售流水，同时维护一份「真实存量」，配传感器的货位按真实值加噪声上报；真实存量与系统估算的差距（损耗、放错位置）显示在控制台。

### 3.6 模拟器闭环（不影响 Phase 1 结果）

- 新模块默认关闭；`simulateDay` 只在传入货架存量对象时改用它判断「货架上有没有」，否则仍按原来的概率，Phase 1 的对比结果逐项不变。
- 店内销售按商品热度和到店客流生成，线上拣货从同一货位扣减；补货任务由后仓补取员在空闲时执行，轨迹（去后仓取箱 → 到货架上架）在场景中可见。
- 输出每个货架段随时间的存量（平均填充率与空货位数），场景新增「库存」叠加层，事件列表记录货位变空、Exception、补货完成，点击可以定位。

## 6. 实施结果与偏差

- **完成**：4a–4f 全部完成，新增 19 个测试（作业核心库存 9、标签 1、后端集成 6、模拟器引擎 3），全部测试 138 个通过；Phase 1 的对比实验输出与提交时的引擎逐字节一致。
- **偏差一：存量按商品记录**。最初按货位记录，但一个货位通常并排陈列几个商品，估算和任务去重会互相覆盖；改为按商品记录，货位只用于找位置和扫描确认。
- **偏差二：货架容量按总需求配置**。最初容量只够卖 6 小时、且只按店内销售估算，模拟器里 38% 的拣货行找不到；改为满架约 1.5 天、按「店内销售 + 线上订单」的总需求配置后，找不到降到约 3%，与 Phase 1 的概率模型接近。
- **偏差三：模拟器增加白天补货员**。只有一名后仓补取员时，Exception 优先，低库存补货任务一直排不上；开启货架存量模型时后仓补取岗位在营业时间内每小时多 1 人。
- **偏差四：陈列表与库位生成放进 algorithms**。原计划放在作业核心，但模拟器也要用，移到公开的 `packages/algorithms`，作业核心再导出。
- **发现的问题**：期初库存把大类分区的第一个库位放满后测试仍选它上架（改为选有空余的库位）；两处后端集成测试读取客户端状态时没等推送到达（改为等待具体订单的批次和事件序号）；货架叠加层最初只要有一个空商品就整段标红，几乎全店变红（改为按空商品占比）。
