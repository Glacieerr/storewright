# 决策记录 0011 · Phase 6 计划：可插拔的扩展业务模块与第二个行业模板

> 日期：2026-10-22 · 状态：已完成（结果见第 6 节）
> 范围来自 [评估与路线图](../05-evaluation-and-roadmap.md) Phase 6 与 [决策记录 0010](0010-roadmap-and-phase5-plan.md) 第 6 节；流程来自 [工作流设计](../01-workflow-design.md) 4.3、4.8、4.9、4.10 节。

## 1. 目标与验收

- 每个扩展模块可以在门店配置中单独开关（路线图验收标准）；关闭时相关命令被拒绝、界面不显示。
- 每个模块都有一个 AI 接入点，与 Phase 5 的建议记录和采纳统计打通。
- 用同一套核心做一个其他行业的门店模板，并记录哪些部分改了、哪些直接复用，作为「流程可以迁移到不同行业」的证据。
- 每个模块按统一的接入流程建设：流程设计 → 决策记录 → 门店配置 → 实现 → 测试 → 文档（流程模板本身不在公开仓库中）。

## 2. 模块框架

作业核心新增 `packages/ops/src/modules/`：每个模块是一个对象，声明自己的命令集合、命令处理、事件应用、排程（可选），以及「是否启用」（读门店静态数据里的模块开关）。`decide` 遇到模块命令时先检查开关，关闭时拒绝（`MODULE_DISABLED`）；`applyEvent` 和 `Tick` 依次交给各模块。状态里每个模块有自己的一块。

| 模块 | 配置开关 | 主要状态 | AI 接入点 |
|---|---|---|---|
| 熟食现做（MTO） | `modules.mto` | 现做单：排队 → 制作中 → 保温中 → 已取出 / 已丢弃 | 出餐时间预测：按菜品和当前负荷预测制作时长，调整「建议开始时间」（建议记录，默认自动执行） |
| 退货 | `modules.returns`（新增） | 退货单：逐件扫描 → 去向 → 完成（发出退款事件） | 去向判断：预测能否再售，建议回架 / 报废 / 危险品回收 / 退供应商；员工是否采纳计入统计 |
| 大件（GM-Oversized） | `modules.gm` | 大件：待领取 → 已领取 → 已贴签 → 已暂存 | 装载规划：按重量与是否需要两人搬运，把一单的大件分成几趟；员工输入自己这一趟的装载上限（决策 P-07） |
| 包裹中转（Parcel Hub） | `modules.parcelHub` | 包裹：预期到货 → 已入站 → 已暂存 → 已交接；短少 / 多出 / 损坏 | 格位分配：同一行程放在一起、按尺寸选格位、靠近门口优先 |

## 3. 各模块的关键规则

- **熟食现做**：建议开始时间 = 时段起点 − 制作时长 − 缓冲 10 分钟；完成后放入保温区并计时，超过保温时限由排程自动丢弃；交付准备时取出（准备时最后取热食）。
- **退货**：顾客退货逐件扫描并核对原订单（不在原订单里的商品标记出来）；配送退回整单处理；去向为可售回架（货架估算增加）、报废、危险品回收、退供应商；完成时发出「退货完成」事件，退款由外部系统处理。
- **大件**：先扫后打，一件一签（标签显示 1/3、2/3、3/3）；员工领取时输入这一趟能装载的件数，剩下的留给别人；超过 23 公斤的件标为两人搬运；暂存在大件区（区域级位置）。
- **包裹中转**：到货通知（ASN）先到；扫描包裹编码入站，没有通知的标为多出、放到待核实区；超过预计到货时间 + 宽限期仍未入站的标为短少；损坏的放到损坏区；按行程暂存，司机交接时整行程确认。

## 4. 第二个行业模板：家居建材

- 选择理由：与超市差别最大——没有冷链和年龄限制，大件和多件商品多，订单以 GM 为主，周末和早上（施工队）是高峰；能检验大件、退货、包裹中转模块，以及仿真引擎、AI 预测在另一种需求形态上的表现。
- 新增：门店配置模板（通道布局、品类、大件区）、合成商品原型（工具、五金、油漆、电工、水暖、园艺、板材、家电）、需求场景、操作规范补充。
- 复用：领域模型、规则引擎、分框分批、仿真引擎、作业核心、员工端、AI 框架与模型（重新用本店数据训练）。
- 记录：`docs/12-business-modules.md` 中列出改动与复用的部分、对比实验结果。

## 5. 不在 Phase 6 范围内

- 外部系统适配器（订单平台、配送平台、承运商、POS 的真实接口），演示中由控制台代替。
- 熟食区的食材库存与配方管理；退货的退款计算规则（只发出事件）。

## 6. 实施结果与偏差（2026-10-22）

- **模块框架与四个模块按计划完成**：`packages/ops/src/modules/` 下每个模块一个文件，注册表登记；关闭时拒绝 `MODULE_DISABLED`；回放事件日志得到相同状态。员工端新增「扩展」页（按岗位默认打开对应模块），控制台可以下带现做和大件的订单、发送包裹到货通知、代替司机交接。详见 [扩展业务模块与第二个行业](../12-business-modules.md)。
- **AI 接入点**：熟食开始时间（菜品系数 + 负荷，离线平均误差 6.4–7.3 → 1.8 分钟，默认自动执行）、退货去向（超市正确率 82.3% → 83.4%；建材店与规则相同，上线门槛保留规则）、大件装载规划、包裹格位建议（规则打分）。
- **偏差 1：大件领取改为可以指定件**。原计划「输入这一趟的件数」按顺序领取，与装载规划给出的分趟不一致；`ClaimOversized` 增加可选的 `pieceIds`，员工端直接领取「第 1 趟」。
- **偏差 2：大件标签复用取货框标签版式**，加了「件」类型（显示 PIECE 1/3），没有单独设计新标签。打印改为员工点按钮（扫码后自动弹出新窗口会被浏览器拦截）。
- **偏差 3：迁移暴露了两处超市默认假设**：「化学品与食品分开装框」把所有散件当成食品（新增商品的非食品标记，只有建材店商品带这个标记）；订单类型 `GROCERY` 的命名沿用为「拣进取货框的散件」，记录为命名债。
- **偏差 4：建材店排班需要单独校准**。直接按订单量缩放时总排班 134 小时、实际作业 28 小时；按与超市相同的口径（拣货利用率、平均等待）校准为 93 小时。
- **第二个行业的结论**：同一套功能在两个行业里回报来源不同——建材店的分批和路线几乎没有作用（每单约 1 框），主要收益是安全（17.6% 的框超重 → 0）、门口停留和满足率；AI 排班在早高峰明显的建材店作用更大（90 分位等待 −9.7 分钟、迟到订单 9.9% → 约 0%）。这支持「先用本店配置跑仿真，再决定打开哪些功能」的接入方式。
- **Phase 1 结果不变**：超市的对比实验逐字节相同（行业参数缺省时走原来的路径，季节性倍数恒为 1）。
- 新增命令：`npm run industry-report`；`STORES=demo,hardware` 同时运行两个门店。测试 187 个（新增模块、指定件领取、建材模板、建材需求形态、建材仿真、两个门店的服务端测试）。
