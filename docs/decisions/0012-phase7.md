# 决策记录 0012 · Phase 7：浏览器内演示、端到端测试、持续集成与部署准备

> 日期：2026-10-22 · 状态：已完成（部署与公开等待作者确认）
> 范围来自 [评估与路线图](../05-evaluation-and-roadmap.md) Phase 7 与 [决策记录 0010](0010-roadmap-and-phase5-plan.md) 第 7 节；说明文档见 [浏览器内演示、端到端测试与部署](../13-demo-and-deployment.md)

## 1. 目标

- 一个从未接触过本项目的人，打开一个网址就能看到完整、可运行的系统（路线图验收标准），不需要安装、不需要后端。
- 用多浏览器端到端测试代替真机验收；持续集成跑类型检查和全部测试。
- 部署、上传、个人网站上线都需要作者确认，本阶段只准备好配置和材料。

## 2. 决策

| 编号 | 决策 | 理由 |
|---|---|---|
| D7-1 | 把服务端的接口逻辑抽成与传输方式无关的门店中枢（`hub.ts`），存储和平台能力（哈希、随机数）注入；Fastify 只是外壳 | 浏览器内演示和本地后端跑同一份代码，演示网页的行为就是真实系统的行为；重构有 30 个接口测试保护 |
| D7-2 | 浏览器里的中枢放在 SharedWorker，内存存储 | 同一个网站的所有标签页和 iframe 共用一家店，实现「多台设备实时同步」的演示；内存存储简单，每次打开都是新店 |
| D7-3 | 不用 PGlite 的浏览器版本，而是另写内存存储 | 存储接口只有几种操作；省掉几 MB 的 WebAssembly，首屏更快 |
| D7-4 | 模拟器经员工端的桥接页面拿到中枢端口 | SharedWorker 按脚本地址区分实例，两个应用各自打包会得到两个实例；桥接页面让两个应用共用一个 |
| D7-5 | 端到端测试用 Playwright，本机用已安装的 Chrome，不下载浏览器 | 依赖小（约 14 MB），持续集成里再安装自带的 Chromium |
| D7-6 | 演示站点用相对路径，组装成一个纯静态目录 | 可以放到任意静态托管和个人网站的任意子路径 |
| D7-7 | GitHub Pages 工作流只能手动触发 | 遵守「上传和部署需要作者确认」 |

## 3. 结果

- 浏览器内演示：员工端演示构建（门店中枢 Worker 约 412 KB）、标签页面、桥接页面、展示页；模拟器的「门店实况」可以连到浏览器里的中枢。两个门店（中型超市、家居建材店）都能在浏览器里打开。第一次打开门店时在浏览器里建店并训练 AI 模型，约 1–2 秒。
- 端到端测试 6 个场景全部通过（约 25 秒）：四台设备走完一张订单、补货闭环、AI 建议、两个标签页同步、展示页、第二个行业（质量改进后增加到 9 个，见第 6 节）。
- 单元与集成测试新增：中枢在内存存储上的完整流程、纯 TypeScript SHA-256 与 Node 结果一致、base64url 与随机整数。
- 持续集成（`ci.yml`）、演示站点部署（`pages.yml`，手动触发）、后端 Dockerfile、站点组装脚本（`npm run build:site`）。
- 英文版 README（`README.en.md`）。

## 4. 偏差与发现

- **偏差 1：浏览器里的本地助手不运行语言模型**。决策记录 0010 计划访客可以选择用 WebGPU 在浏览器里运行小模型；本阶段只用规则 + 本地意图分类器（与没有配置语言模型的后端相同），WebGPU 留到以后。
- **偏差 2：`.env.demo` 会被 `.gitignore` 的 `.env.*` 规则忽略**，持续集成里会丢失演示开关；改为在 Vite 配置里按构建模式定义。
- **发现：端到端测试的竞态**。测试连续点击「已拣到」时，上一次点击还没反映到界面就点了下一次；测试改为等进度变化再点。应用本身没有问题。
- **发现：服务端测试偶发一次暂存失败**（重构后第一次运行，之后连续通过）；断言加上了拒绝原因，以便再次出现时定位。

## 6. 总测试之后的质量改进（2026-10-22）

总测试通过后，作者选择先做改进清单里的四项质量改进，再整理提交：

- **退货的硬性规则**（决策 RT-02 原本已采纳，Phase 6 只做了 AI 建议）：作业核心按规则拒绝不安全的去向（冷链食品回架、散件开封回架、损坏回架、化学品进普通垃圾、开封的化学品不走危险品回收），员工端把这些去向设为不可选并说明原因，AI 建议只在允许的去向里给出。退货行记录化学品和「只能未开封回架」两个标记（旧事件没有时按 false 处理）。
- **演示数据保存**：浏览器内的中枢写入 IndexedDB，刷新或关闭所有页面后门店还在；12 小时没有写入时清空作业事件；展示页加「重置演示门店」。
- **展示页引导**：6 步引导按门店的实时状态自动打勾，当前步骤给出具体操作；可以收起。
- **窄屏布局**：900 像素以下一次显示一个画面（控制台、手机 1、手机 2、模拟器），用标签切换。
- 新增测试：作业核心的规则测试、服务端的规则测试、3 个端到端场景（退货规则、引导与数据保存、窄屏布局），端到端共 9 个场景。


## 7. 全流程走查（2026-10-22）

作者要求执行全流程测试，以便判断所有流程和更多细节。新增走查（`npm run walkthrough`，见 [13 §5b](../13-demo-and-deployment.md)）：11 个部分在真实浏览器里操作员工端、控制台、浏览器内演示、模拟器、接口和命令行，每一步记录结果、用时、细节和截图，生成图文报告。

走查发现并修复的问题（每一项都加了测试）：

| 问题 | 原因 | 修复 |
|---|---|---|
| 开门后还没卖出就丢失的商品，AI 发现不了 | 可售概率扫描跳过还没有货架记录的商品；没卖过的商品「本应卖出几件」按时钟估计，加速仿真里时钟几乎不走 | 没有记录的商品按满货架处理；沉默按全店销量折算（从上次卖出、员工上次确认或开始接收流水算起）；约 4 个仿真小时发出提醒 |
| 破损箱上架时没有库位建议 | 库位建议只按「可售」检查 | 按箱子的库存状态建议（待检、退供应商、报废） |
| 年龄核验没做完时「完成交付」也能点 | 只有作业核心拒绝 | 核验前按钮不可用，并说明原因 |
| 展示页里模拟器只剩一条窄带，控制台的「创建」在框外 | 嵌入时仍显示完整的顶栏、时间轴、数据面板和统计卡片 | 嵌入模式只留场景、视角和门店实况状态条；控制台隐藏统计卡片 |
| 控制台「实时事件」显示内部英文事件名 | 52 种事件没有中文名称 | 91 种事件全部有中英文名称；新增事件没有名称时测试失败 |
| 门店编号填错时提示「连不上服务器」 | 不区分错误类型 | 门店不存在时提示检查门店编号 |
| 连续操作时提示条叠在一起，挡住内容 | 提示条没有数量上限 | 最多两条，按类型自动消失，点击关闭 |
| 两家店的订单短号可能相同 | 同一个盐、订单编号相同 | 短号里含门店编号 |
| 问「周末烤鸡放在哪」时，助手没用刚记下的门店经验 | 识别为找商品后，陈列表里找不到就结束 | 找不到时再查门店经验（只认和商品名重合的经验） |

说明（不是问题）：有货架传感器的商品由传感器直接发现，不需要 AI 推断；没人补货时，长时间的购物仿真里缺货会越积越多；回滚只能回到更早上线过的版本。

### 7.1 走查观察到的 3 个细节（作者要求在提交前修改）

| 细节 | 原因 | 修改 |
|---|---|---|
| 送货行程大多只有 1 单 | 离必须出发不到 15 分钟时，排程立刻把已暂存的订单组成行程；同一时段的另一单还在拣货，于是各自单独成行 | 同一时段还有订单在拣货、暂存时先等它们（剩 5 分钟以内不再等）；走查里两张订单组成一趟 |
| 「下午 3 点到 6 点交付多一个人」推演结果不变（4 → 4 分钟） | 真正的原因是助手忽略了「下午」，推演跑在凌晨 3–6 点（那时没有交付员） | 能读「下午 / 晚上 / 中午」「pm」；结果几乎没变时用仿真数据说明原因（这个时段排了几个人、每人每小时几单、岗位全天忙碌比例），并指出每人负担最重的时段 |
| 没人补货时缺货越积越多 | 演示门店没有补货的员工 | 控制台加「自动补货」开关（默认关闭）：虚拟补货员按优先级处理补货任务；货架核对仍由员工去做 |

每一项都加了测试，走查也检查了结果（两单一趟、推演时段 15–18 点、自动补货完成任务）。

走查脚本本身也修了一些等待和定位的问题（例如送货行程在暂存后才生成，而不是锁单时）。这些都不是应用的问题。
