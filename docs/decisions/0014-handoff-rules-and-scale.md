# 决策记录 0014 · 交付规则调整与大型店容量升级

> 状态：完成（2026-10-22）
> 作者要求（原话要点）：交付时填写错误的取货码，不需要有剩余次数的限制；送货司机接单后，可以在被系统标记抵达的最后十分钟以外取消，进入十分钟的准备期后则不允许取消，接单后到店等待超过十分钟，司机可以选择取消，系统要做出相应的一系列应对；系统可能扩展到大型店铺，员工可能有几百人，需要在容量、及时等层面升级。

---

## 1. 取货码输错不限次数

**原来**：连续输错 3 次（`rules.handoff.codeAttempts`）后锁定验证码输入，只能人工核验。
**现在**：
- 输错不限次数、不锁定，员工看到「验证码不正确（已错 N 次），请顾客再核对一遍」；
- 错到 `codeAttempts` 次后，在输入框下面多一个「也可以改用人工核验」的入口（核对证件和订单信息），验证码仍然可以继续输入；
- 每次输错仍然记录事件（`CodeFailed`，次数可审计）。

配置项 `codeAttempts` 的含义改为「错几次后提供人工核验入口」；事件字段名 `manualRequired` 沿用（含义是入口已提供），旧数据不用迁移。拒绝原因 `MANUAL_REQUIRED` 删除。

## 2. 配送司机取消接单

### 2.1 时间窗口（`packages/ops/src/driverCancel.ts`，作业核心、控制台、司机端共用）

| 时间 | 司机能否取消 | 说明 |
|---|---|---|
| 接单后、预计到店前 10 分钟以外 | 可以 | 门店还没进入准备期 |
| 预计到店前 10 分钟起（准备期）到司机到店 | 不可以（`CANCEL_LOCKED`） | 门店已经按这个时间备货 |
| 到店后不满 10 分钟 | 不可以（`CANCEL_WAIT`，附带还要等多久） | |
| 到店后等满 10 分钟 | 可以，记为「等待过久」 | 门店原因 |
| 没有预计到店时间 | 到店前都可以 | |

两个 10 分钟是门店规则 `rules.handoff.driverCancelLockMin`、`driverCancelWaitMin`（可选，默认 10）。只有司机本人能取消：经平台（操作者 `driver`），或演示控制台代为操作；员工不能代替司机取消。

**司机没来**：预计到店时间过了 10 分钟还没到（没有预计时间时接单满 60 分钟），带班负责人或控制台可以「改派」（`RedispatchTrip`），处理方式和司机取消相同，原因记为 `NO_SHOW`。

### 2.2 系统的应对（一条事件 `TripDriverCancelled`）

1. **重新派单**：行程回到「等待司机接单」，司机、验证码、预计到店、到店信息清空；记录取消历史（谁、什么原因、等了多久），控制台显示「重新派单 · 已取消 N 次」；新司机接单得到新的验证码，旧的作废。
2. **结束交付准备**：如果员工已经开始准备，会话结束，订单回到「已暂存」。
3. **已取出的框放回暂存区**：优先放回原格位，原格位满了就放同温区有空位的格位；交付员手机上列出每个框要放回哪个格位（冷藏、冷冻框尽快放回）。
4. **通知顾客**：订单记录送达延后的通知时间（`delayNoticeAt`）。
5. **超时预警**：离送达时段结束不足 20 分钟（重新派单大约要这么久）时标记「可能超时」，交付员手机和控制台提示通知带班负责人。
6. **统计**：取消原因分为「准备期之前」「等待过久」「司机没来」；「等待过久」是门店原因，可以接到交付人手和 AI 排班的分析里。

### 2.3 界面

- 演示控制台的配送行程：司机接单、「预计 15 分钟后到店」、司机到店、「司机取消接单」（不在窗口内时按钮不可用，并说明原因和还要等多久）、「司机没来，改派」；
- 交付员手机：行程被取消时显示原因、重新派单次数、要放回的框和格位、顾客已收到延后通知。

## 3. 大型店容量升级（300 名员工）

### 3.1 测量方法

`npm run loadtest -w @storewright/server`（`apps/server/src/loadtest.ts`）：一家两层的大型店（门店编号 `large`，300 名员工，按岗位比例生成名单），全部在一个进程里运行：
1. 一天 1200 张自取订单走完拣货 → 暂存 → 到店 → 交付（约 3 万条命令）；
2. 一天结束时门店状态的大小；
3. 开班：300 台设备同时连上；刷新页面后重新连上；
4. 高峰：60 人同时提交 3000 条命令（压到饱和）；
5. 平稳高峰：每秒 50 条命令（300 人的门店忙的时候大约每人每 6～10 秒一次操作）。

`DB=pglite` 时每条命令真的写进数据库（内存里的 PGlite），`DATABASE_URL` 指向 PostgreSQL。

### 3.2 发现的问题

- 每条推送对每台设备各序列化一次：300 台设备时同一段 JSON 算 300 遍；
- 每台设备连上时都收到整份状态：一天下来 6.8 MB（其中大半是早已完成的批次、框、标签、交付会话）+ 1.7 MB 静态数据（陈列表、库位、名单），300 台就是 2.5 GB；
- 每条事件单独推送：高峰时每台设备几千条消息。

### 3.3 改了什么

| 改动 | 位置 |
|---|---|
| 推送只序列化一次，所有设备共用同一段文本 | `apps/server/src/hub.ts`（`frameOf`） |
| 推送合批（只用于设备连接）：空闲时立即推送；忙的时候 15 毫秒内的事件合成一条消息（最多 256 条事件）。门店里的服务（AI、自动运营、客流仿真）仍然每条命令立即收到——测试发现合批会让 AI 晚一步看到收银流水 | `apps/server/src/runtime.ts` |
| 设备快照精简：完成超过 1 小时的批次、框、标签、交付会话不发，订单只留摘要（服务端状态不变） | `packages/ops/src/projection.ts`（`clientProjection`） |
| 快照缓存：同一序号、同一分钟内的新连接共用一次序列化 | `hub.ts`（`snapshotFrame`） |
| 静态数据带版本：设备保存在本机，版本相同时快照里不再带 | `hub.ts`、`packages/ops/src/client.ts` |
| 登录页：名单多时可以搜索名字或员工编号、按岗位筛选（输入编号回车直接登录） | `apps/associate/src/screens/SignIn.tsx` |
| 控制台的进行中订单表最多列 150 张 | `ConsoleScreen.tsx` |
| AI 调动建议：每人完成数先统计一次，不在排序里反复遍历 | `apps/server/src/ai.ts` |

### 3.4 结果（同一台开发机，内存存储）

| 指标 | 改前 | 改后 |
|---|---|---|
| 300 台设备同时连上 | 6.5 秒，共发出 2.5 GB | 0.09 秒，1.1 GB（每台约 3.6 MB） |
| 刷新后重新连上（已有静态数据） | 同上 | 每台约 1.9 MB |
| 饱和吞吐 | 739 条/秒 | 2792 条/秒 |
| 饱和时提交到所有设备收到 p95 | 83 毫秒 | 22 毫秒 |
| 饱和时每台设备收到的消息 | 约 5900 条 | 53 条 |
| 平稳高峰（每秒 50 条）提交到所有设备收到 p95 | — | 15 毫秒 |

写入数据库时（内存里的 PGlite，300 张订单）：单条命令 p95 0.8 毫秒，平稳高峰 p95 16.5 毫秒；饱和吞吐约 620 条/秒，瓶颈是逐条串行写库。真实网络上 WebSocket 还会压缩（快照约压到 1/8）。

### 3.5 还可以继续做的（按需要）

- **成组提交**：饱和时把排队的多条命令放进一次数据库事务，吞吐可以再提高几倍（现在的余量约是 300 人门店高峰的 10 倍，暂不需要）；
- **多店横向扩展**：每家店一个运行时、互不依赖，可以按门店分到多个进程或机器；
- **按岗位订阅**：设备只订阅自己需要的数据（例如拣货员不需要后仓箱子），需要把客户端改成部分副本；
- **归档**：每天结束后把完成的订单移到历史表，服务端内存只留当天。

## 4. 测试

- 作业核心：取货码输错 6 次后仍能输入正确的码，人工核验入口已提供；司机取消的完整过程（准备期外取消 → 准备期内被拒 → 到店不满 10 分钟被拒 → 等 11 分钟取消，框放回原格位、会话结束 → 司机没来时改派 → 新司机接单照常交付，重放事件得到同样的状态）；设备快照精简后统计不变、之后的事件照常应用；
- 中枢：控制台代替司机取消、员工不能代替；300 人的大型店；合批推送序号连续、两台设备收到同样的推送；已有静态数据的设备不再收到；
- 走查第 2 部分：取货码输错 4 次不锁定、出现人工核验入口；第 3 部分：司机上报预计到店、准备期外取消、重新派单、第二位司机接单、到店不满 10 分钟不能取消。
