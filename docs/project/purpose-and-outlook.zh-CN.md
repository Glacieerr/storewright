# 项目目的、达成的目标与未来展望

[English](purpose-and-outlook.en.md) · [项目报告](project-report.zh-CN.md) · [操作指南](../guide/operation-guide.zh-CN.md) · [完整中文说明](../../README.zh-CN.md)

> 本项目基于公开资料、行业通用做法和作者的独立构想设计。**本项目与任何零售商、企业无隶属关系。** 所有门店、商品、顾客和数字都是合成的；文中的结果都是证据等级 B（在列明的假设下仿真得到），不代表任何真实门店。
>
> 状态截至 2026-10-26。

## 1. 为什么做这个项目

### 1.1 背景

超市的线上订单越来越多，大部分在门店里完成：员工推着车在货架间拣货，放进暂存区，等顾客到店或司机来取。公开资料里能看到这种做法的几个难处：

| 难处 | 公开数字 | 来源 |
|---|---|---|
| 门店拣货靠人工，效率有天花板 | 人工拣货约每工时 60–70 件；一张约 30 件的订单要花约 30 分钟拣货工时（咨询公司估算，2022） | [咨询公司报告](https://www.mckinsey.com/industries/retail/our-insights/achieving-profitable-online-grocery-order-fulfillment) |
| 顾客到店要等 | 神秘顾客调查：路边取货平均等 5 分 21 秒（2019，8 家连锁）、3.5 分钟（2020，4 家） | [行业媒体](https://www.grocerydive.com/news/h-e-b-whole-foods-have-fastest-pickup-times-study-says/566152/)、[调研机构](https://storesight.com/resources/which-retailer-has-the-fastest-ogp-grocery-pickup-time) |
| 库存记录不准，导致缺货和替代 | 一项研究里 65% 的门店库存记录不准（2008）；一次盘点让门店销售提高 11%（2025） | [论文](https://pubsonline.informs.org/doi/10.1287/mnsc.1070.0789)、[论文](https://arxiv.org/abs/2506.05357) |
| 网购占比还在涨 | 美国网购生鲜占生鲜消费的 20.9%（2026 年第三季度） | [行业媒体](https://theshelbyreport.com/2026/10/15/u-s-e-grocery-sales-climb-21-in-q3-capture-record-share/) |

大型连锁已经有成熟的系统，真正缺这类系统的是**中型区域连锁和独立超市**（[03 号文档 G-03](../03-open-questions.md)）。

### 1.2 目的

1. **做一套面向中型和独立超市的门店数字孪生**：线上订单履约（拣货 → 暂存 → 交付）、后仓库存、货架补货、人员调配和门店 AI 放在同一个核心上；三维门店和现场作业实时同步，可以回放当天任意时刻、推演未来 3 小时；改布局、排班、策略之前，先在规划孪生里试。
2. **让每家店都能定制**：布局、规则、模块、AI 模型都按店配置，同一套代码还能迁移到别的行业。
3. **用证据说话**：每个改进都在仿真里和基线对比，写清楚假设、置信区间和代价，不夸大。
4. **作为作品集**：向所有人展示一整套门店工作流解决方案的构想、实践和规划能力，从理解门店业务、设计产品，到工程实现、测试和诚实评估；整个系统能直接在浏览器里运行，打开网页就能看。全部内容都在本仓库，没有付费功能或商业服务，见 [README 的「许可证」](../../README.zh-CN.md)。

## 2. 开始时定下的目标

Phase 0（2026-10-18）冻结了需求和约束（[03 号文档](../03-open-questions.md)、[决策记录 0001](../decisions/0001-phase0-decisions.md)、[05 号文档](../05-evaluation-and-roadmap.md)）：

| 编号 | 目标 | 验收方式 |
|---|---|---|
| G1 | 核心履约在员工手机上跑通，并且比没有专门系统的门店更安全、更快 | 仿真对比实验 |
| G2 | 后仓、补货、人员调配接进同一个核心 | 功能和测试 |
| G3 | 门店 AI 本地优先、每店定制，比简单方法好才上线 | 离线评估、上线门槛 |
| G4 | 2.5D / 3D 模拟器纯前端运行，能对比策略，流畅 | 性能测量 |
| G5 | 配置驱动，能迁移到另一个行业 | 第二个行业模板 |
| G6 | 结论诚实：证据分级、置信区间、消融、敏感性分析 | 报告能逐行复现 |
| G7 | 合规：只用公开信息、中性命名、写明无隶属关系 | 自查 |
| G8 | 可展示：一个从没接触过的人 5 分钟内看懂做了什么、证明了什么 | 浏览器内演示、双语文档 |

## 3. 达成了什么

| 目标 | 结果 | 依据 |
|---|---|---|
| G1 履约 | ✅ 拣货、暂存、交付、配送行程都在手机上跑通。仿真（中型店，30 次重复）：超重、压坏风险、化学品混装的框从 11–19% 降到 0；订单满足率 +1.0 个百分点；平均到店等待 −15%；订单在门口停留 −81%；代价是作业工时 +4.9%（效率优先档位 +0.4%） | [06 Phase 1 成果](../06-phase1-results.md) |
| G2 后仓、补货、人员 | ✅ 收货、上架、盘点、后仓补取、货架存量估算、按推车装载量分批补货；排班草稿可以改、改后重新打分；在岗人员和临时调人，到时间自动调回 | [09](../09-backroom-replenishment.md)、[决策记录 0025](../decisions/0025-team-view-dispatch.md)、[0026](../decisions/0026-flow-fixes.md) |
| G3 门店 AI | ✅ 订单量、到店时间、可售概率、盘点、替代、排班等模型在本机训练，过了上线门槛才用；建议都写明理由，连续不准自动降级。工时不变时打开全部 AI：平均等待 −13%，90 分位等待 −23%，迟到订单 2.41% → 0.69% | [10](../10-store-ai.md)、[11 AI 效益报告](../11-ai-results.md) |
| G4 模拟器 | ✅ 中型店在 1440 × 900 高分屏上 6 种画质和视角组合都是 60 fps，每帧主线程约 4 ms；全天仿真、策略对比、门店编辑器、AI 运营建议 | [07 运营模拟器](../07-simulator.md) |
| G5 迁移 | ✅ 同一套核心迁移到家居建材店；收益从分批转向安全和 AI 排班 | [12 扩展模块与第二个行业](../12-business-modules.md) |
| G6 诚实 | ✅ 公共随机数配对实验、95% 置信区间、消融、敏感性分析；基线刻意设得偏强；Phase 1、AI 和行业报告能逐行复现 | [05 第一部分](../05-evaluation-and-roadmap.md)、[06](../06-phase1-results.md) |
| G7 合规 | ✅ 信息边界写成规则（G-02），中性命名，所有文档写明无隶属关系；第三方组件 199 个，全部宽松许可 | [合规声明](../../COMPLIANCE.md)、[第三方组件声明](../../THIRD_PARTY_NOTICES.md) |
| G8 可展示 | ✅ 整个系统可以在浏览器里运行：展示页同时显示控制台、两部手机、三维数字孪生和全天仿真；中英文 README 和英文技术概览 | [13 演示与部署](../13-demo-and-deployment.md)、[英文技术概览](../en/overview.md) |

做的过程中还扩展了几块原来没计划的内容：

- **你的商店**：从一块空地搭建自己门店的孪生，按占地等条件生成、逐项编辑、开业检查，然后跑全天仿真或开实时沙盒；门店保存在浏览器里，可以复制、导出和导入（[决策记录 0013](../decisions/0013-phase8-plan.md)）；
- **数字孪生**：设备遥测与告警闭环（越线时带着受影响的订单、框、箱推到带班负责人的手机）、回放、推演、孪生健康度（[14 数字孪生](../14-digital-twin.md)）；
- **门店 AI 第二轮**：运营预警、少打扰的建议中枢、排班与缺勤补位、预测性维护、打烊复盘、召回、突发状况、食品安全记录、临期降价、每个人的「下一步」（[15 路线图](../15-store-ai-roadmap.md)、决策记录 0021–0024）；
- **流程梳理和修复**：逐个岗位梳理所有操作步骤，修好 18 个会卡住的状态，再实施 25 条简化（[16 操作流程](../16-operation-flows.md)）；
- **容量**：按 300 人的大型店测试，300 台设备 0.09 秒连上，每秒 50 条操作时所有设备约 15 毫秒内看到变化。

规模：4 个应用、9 个共享包，约 8.2 万行 TypeScript 源代码；383 个单元与属性测试，83 个多浏览器端到端测试（含无障碍检查），22 个部分、221 步的全流程走查；16 份设计文档、27 条决策记录。

## 4. 没有做到或者有意简化的

- **没有真实门店的数据，也没有现场试点**。所有结论都来自合成数据上的仿真，用来比较方法，不是对真实门店的预测。
- **演示没有真正的登录**（从名单里选身份）。正式部署需要登录、角色权限和会话过期（[08 第 7 节](../08-live-operations.md)）。
- **本地语言模型、语音和视觉模型还没有下载**。接口和评测都准备好了，下载需要作者同意（[10 第 10 节](../10-store-ai.md)）。
- **真实设备没有联调**。演示里的温度、门磁读数由仿真产生（[14 第 11 节](../14-digital-twin.md)）。
- **运营上的 A/B 还没有做**。AI 第二轮各批没有完成的验收项写在各决策记录的最后一节。
- **个人网站的项目页还没上线**：[GitHub 仓库](https://github.com/Glacieerr/storewright)和[在线演示](https://glacieerr.github.io/storewright/)已经在 2026-10-29 发布。

## 5. 未来展望

### 近期：发布

1. ✅ 本机按阶段提交，作者确认后在 GitHub 公开仓库（2026-10-29）。
2. ✅ 用 GitHub Pages 部署浏览器内演示，README 补上在线演示地址，演示页右上角加上源代码链接（2026-10-29）。
3. 个人网站加项目页：截图、演示视频、项目报告。

### 中期：验证

1. 用公开数据集校准作业时间、到店时间和缺货率，减少对假设的依赖。
2. 真机联调：蓝牙扫码枪、标签打印机、温控器和门磁。
3. 正式部署需要的部分：登录与权限、HTTPS、依赖漏洞审计。
4. 作者同意后下载一个小的本地语言模型，做和模板模式的对比评测。
5. 要用真实结果检验第 3 节的数字，需要真实门店的匿名数据、一条流程的小范围试点（例如只做交付）和运营上的 A/B。本项目是作品集，这里写明的是需要什么样的验证。

### 长期：作品集

1. 本仓库作为公开的作品集持续更新：新的构想先在仿真里验证，再写进文档和决策记录（[决策记录 0027](../decisions/0027-portfolio-license.md)）。
2. 更多行业模板（例如药房、便利店），更多可选模块。
3. 货架传感的硬件原型（[货架传感原型指南](../hardware/shelf-sensing-prototype.md)）。

不变的原则：只用公开信息；每个结论都写明证据等级和假设；门店数据留在门店；先在仿真里试，再改现场。
